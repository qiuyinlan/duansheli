# 中英双语的写法约定

给以后改这个项目的人（也包括 AI）看。**动手前先读完这一页**，
不然很容易做出「看起来能跑、其实会在切语言时露馅」的东西。

---

## 1. 三层，别搞混

| 层 | 例子 | 怎么处理 |
|---|---|---|
| **界面文案** | 按钮「保存」、「还没有物品」 | 翻译。走 `t()` |
| **用户自己的数据** | 他建的分类「化妆品」、位置「家 / 卧室」、物品名 | **绝不翻译**，永远原样显示 |
| **AI 提示词** | `src/ai/promptText.ts` 里的 system prompt | 两份（中/英），跟着界面语言走 |

最容易犯的错是把第二层当成第一层去翻。记住了：
**你能在界面上改的文字，不一定是你能翻译的文字。**

## 2. 字典在哪、怎么加

```
src/i18n/
  index.ts        运行时：语言状态、t/tc、useT、Intl 封装
  zh/index.ts     中文词典的聚合，同时**定义类型**（唯一真源）
  zh/<区域>.ts    一个界面区域一个文件：common / nav / items / ...
  en/index.ts     英文词典的聚合
  en/<区域>.ts    和 zh 一一对应
```

加一条文案就是**两个文件各加一行**：

```ts
// src/i18n/zh/items.ts
export const items = {
  empty: '还没有任何物品',
}
```

```ts
// src/i18n/en/items.ts
export const items = {
  empty: 'No items yet',
}
```

**少了英文那一行，`tsc` 直接报错。** 这是刻意的：
双语不同步是这类项目最常见的腐烂方式，让编译器替我们盯着。

### 硬性要求

1. **不要写 `as const`。**
   加了它，字典的值会变成字面量类型（`'保存'` 而不是 `string`），
   于是英文永远没法满足 `typeof zh`，类型约束当场失效。
2. **不要改嵌套结构。** 区域文件的导出名、命名空间名要和对面一致。
3. **不要动别人的区域文件。** 一个人负责一个区域，冲突了很难收拾。
4. **不要在模块顶层调用 `t()` 存进常量。**

## 3. 第 4 条为什么要单列

```ts
// ❌ 错的
export const STATUS_LABEL = { active: t('status.active') }

// ✅ 对的
export function statusLabel(s: ItemStatus) {
  return s === 'idle' ? t('status.idle') : t('status.active')
}
```

语言是**运行时**能变的。模块顶层那个 `t()` 会在模块加载的那一刻
把当时语言的文字冻在里面，之后怎么切都不变 ——
于是出现「页面标题变英文了、侧栏还是中文」这种半截状态，
而且很难查。**凡是可能在切换语言后还要重新求值的东西，都写成函数。**

## 4. 在组件里怎么用

```tsx
import { useT } from '../i18n'

export function Foo() {
  const { t, tc, lang } = useT()
  return <button>{t('common.save')}</button>
}
```

`useT()` 不只是给你 `t`，它还**订阅**了语言变化 ——
语言一变，这个组件就会重新渲染。所以：

- 组件里必须有至少一处 `useT()`（或 `useLang()`），否则文字不会跟着切。
- 用 `useMemo`/`useEffect` 且里面用了 `t()` 时，**把 `lang` 放进依赖数组**。
  `t` 是个读模块级状态的普通函数，它自己不会让 memo 失效。

在 React 之外（store、校验、导入导出、API 客户端）直接 `import { t } from './i18n'` 用就行。

## 5. 插值和单复数

```ts
t('nav.footerCounts', { items: 3, idle: 1 })   // 共 3 件 · 闲置 1 件
```

有单复数的地方写成一对，用 `tc(count, 词干)`：

```ts
// zh:  found_one: '{count} 件',  found_other: '{count} 件'
// en:  found_one: '{count} item', found_other: '{count} items'
tc(3, 'items.found')      // → 「3 件」/「3 items」
```

中文那两条写一样的话就行 —— 中文没有单复数，
留着是为了让两份字典**形状一致**，形状一致是类型约束能成立的前提。

`tc` 的词干也有类型约束：`tc(3, 'items.found')` 里拼错的词干编译不过。

## 6. 日期、数字

- **`2025-01-15` 这种格式两种语言都直接用**，不做本地化：
  它没有歧义，而且按字符串排序就是按时间排序。
- 要给人读的本地化写法用 `formatDateLong()`（`2025年1月15日` / `Jan 15, 2025`）。
- 相对时间用 `formatRelative()`（`3 天前` / `3 days ago`）。
- 数字用 `formatNumber()`，别自己拼千分位。

## 7. 语言是怎么定的

1. 用户在右上角手动选过 → 用他选的（存在 `localStorage` 的 `duansheli:lang`）
2. 没选过 → 跟 `navigator.language` 走：`zh*` 给中文，其余给英文
3. 什么线索都没有 → 中文

**种子脚手架（首次启动铺的分类、位置、标签）按当时的语言生成一次**，
之后切语言不会去改动已有数据 —— 你花时间改过的分类名被悄悄翻译掉，
是最让人恼火的一类 bug。

## 8. 测试

- 测试环境**锁成中文**（`tests/dom.ts` 里写死了 `duansheli:lang`），
  所以断言中文文案的老用例不用改。
- 想测英文：`setLang('en')`，**用完记得切回 `zh`**。
  语言是模块级状态，会污染后面的用例 —— 和当年 API Key 那个坑一模一样。
- 语言相关的用例集中在 `tests/i18n.ts`。
