# 断舍离 · 个人物品整理网站 — 设计文档

> 版本 v1.0 · 状态：已定稿，进入实现
> 一句话定位：**一面照出"我到底有多少东西、都在哪、哪些该扔"的镜子。**

---

## 1. 目标与非目标

### 1.1 要解决的问题

东西太多、不知道在哪、不知道有多少、扔不掉。核心诉求是 **极简、清楚、可视化、能下决心断舍离**。

### 1.2 设计原则（所有取舍都回到这四条）

| 原则 | 具体体现 |
|---|---|
| **录得快** | 录入表单默认只显示 1 个必填项（名称）；其余全部可选、默认折叠；回车即保存并继续录下一条 |
| **看得清** | 白底、无阴影、细分割线、大量留白；一屏内不出现超过 3 种字号 |
| **随时换视角** | 同一批数据，按分类 / 按位置 / 按标签 / 按属性自由切换分组，不做多个独立页面 |
| **扔得动** | 「闲置」是一等公民，有独立入口；扔东西是正向流程，不是删除数据 |

### 1.3 明确不做（Non-Goals）

- ❌ **不做照片**：用户明确不需要。换来更快的录入和更干净的界面。
- ❌ **不做用量/保质期提醒、扫码、发票、二手估价**：偏离"断舍离"。
- ❌ **不做多人协作、共享清单**。
- ❌ **不做推荐算法式的"AI 帮你决定扔什么"**：决策权留给人。

## 2. 技术栈

| 层 | 选型 | 理由 |
|---|---|---|
| 构建 | **Vite 5 + TypeScript** | 快、零配置、产出纯静态文件 |
| 框架 | **React 18** | 生态成熟，状态驱动适合筛选/统计这类联动 |
| 路由 | **react-router-dom（HashRouter）** | HashRouter 避免 GitHub Pages 刷新 404 |
| 状态 | **Zustand** | 极轻（~1KB），无 Provider 嵌套，适合单 store |
| 持久化 | **自研薄封装 + IndexedDB** | 见第 5 章，全量数据整体读写 |
| 样式 | **原生 CSS + CSS 变量**（4 个全局样式文件） | 不用 UI 库。极简风格自己写反而更少代码、更可控 |
| 图表 | **手写 div/SVG，不用图表库** | 只需要灰度条形图，引库是负担 |
| PWA | **vite-plugin-pwa** | 手机"添加到主屏幕"，离线可用 |
| AI | **DeepSeek API（浏览器直连）** | 不需后端、Key 不经第三方；CORS 已实测确认（见第 16 章） |
| 测试 | **fake-indexeddb + jsdom + esbuild** | 在 Node 里跑真实的持久化链路与真实 DOM 渲染 |
| 部署 | **GitHub Pages + GitHub Actions** | 免费，推代码即发布 |

**运行时依赖总数：4 个**（react、react-dom、react-router-dom、zustand）。

## 3. 部署与数据存储

### 3.1 部署形态

纯静态 SPA，无后端。构建产物 `dist/` 推到 GitHub Pages。

- Vite `base: './'` → 使用相对路径，仓库名任意都能跑
- HashRouter → 所有路由都在 `#/` 后面，服务器无需任何 rewrite 规则

### 3.2 数据存在哪（必须理解的事实）

数据存在**访问者自己的浏览器**里，不在 GitHub 上。

```
电脑浏览器打开 https://xxx.github.io/duansheli/
        └─ 数据写入 → 电脑浏览器的 IndexedDB

手机浏览器打开同一个网址
        └─ 数据写入 → 手机浏览器的 IndexedDB      ← 与电脑完全独立，互相看不见
```

**结论：手机和电脑是两份独立数据，不会自动同步。** 打通方式见 3.5。

### 3.3 IndexedDB 与其他本地存储的关系

浏览器的本地存储有 4 个互不冲突的 API，可以同时使用：

| API | 容量 | 本项目的用途 |
|---|---|---|
| **IndexedDB** | 几百 MB ～ 数 GB | **主数据 + 自动快照** |
| localStorage | ~5MB，同步阻塞，仅字符串 | 仅界面偏好（如上次选的分组维度） |
| sessionStorage | ~5MB，关标签页即失效 | 不使用 |
| Cache Storage | 大 | PWA 缓存静态资源，实现离线打开 |

### 3.4 GitHub Pages 的存储陷阱（重要）

IndexedDB 按 **origin（协议+域名+端口）** 隔离，而 `https://用户名.github.io/仓库A/` 与
`https://用户名.github.io/仓库B/` 属于**同一个 origin**，共享同一套存储。

因此：

1. **数据库名固定为 `duansheli`**，与其他项目天然隔离，不会互相覆盖。
2. **将来若绑定自定义域名，origin 会改变，旧数据不会自动跟过来**（数据还在，只是"钥匙"变了）。
   → **换域名前务必先导出备份。**
3. 清除浏览器数据、换浏览器、无痕模式、iOS 长期不访问可能被系统回收存储。
   → **导出备份是保命手段，不是可选功能。**

### 3.5 手机 ⇄ 电脑 数据打通

**v1 方案：手动导出 / 导入 JSON。**

```
手机录完 → 设置页「导出 JSON」→ 通过微信/网盘/邮件传到电脑 → 电脑「导入」→ 完成
```

已知不够顺手，但 v1 优先把产品手感做对。

**预留：v2 接 Supabase。** 存储层已抽象成 `Repository` 接口（见 5.2），
届时只需新增 `SupabaseRepository` 并在入口切换实现，**业务代码一行不改**。

## 4. 数据模型

整个应用的数据集是一个纯 JSON 对象，无循环引用、无二进制，因此可以直接序列化、直接导出。

```ts
/** 应用全集 —— IndexedDB 里存的就是这一个对象 */
interface AppData {
  schemaVersion: number;        // 当前 1
  items: Item[];
  categories: Category[];
  locations: Location[];
  attributeDefs: AttributeDef[];
  tags: Tag[];
  updatedAt: string;            // ISO
}
```

### 4.1 物品 Item

```ts
type ItemStatus = 'active' | 'idle' | 'discarded';

interface Item {
  id: string;                   // uuid，将来兼容 Supabase
  name: string;                 // 唯一必填
  categoryIds: string[];        // 多分类（用户选定）
  locationId: string | null;    // 单一位置，可为空（= 未归位）
  quantity: number;             // 默认 1
  status: ItemStatus;           // 默认 active
  tags: string[];               // 自由标签
  attrs: Record<string, AttrValue>;  // key = attributeDef.id，只存填了的
  note: string;
  createdAt: string;            // ISO
  updatedAt: string;
  idleAt: string | null;        // 首次标记闲置的时间（用于算闲置时长）
  discardedAt: string | null;
}

type AttrValue = string | number | boolean | null;
```

**关键设计：**

- `attrs` 是**稀疏字典** —— 只存真正填了值的属性。没勾选的属性在数据里完全不存在，
  这直接实现了「属性可自选加不加」。
- `locationId` 指向位置树的**任意层级节点**，不强制叶子节点。
  你可以把"吸尘器"挂在「家/客厅」，也可以精确到「家/客厅/电视柜/下层」。
- `status: 'discarded'` 是**软删除**。删物品默认进"已舍弃"，数据仍保留，可回顾"我都扔了些什么"。

### 4.2 位置 Location（不限层数树）

```ts
interface Location {
  id: string;
  name: string;
  parentId: string | null;      // null = 顶层（如「家」）
  note: string;
  order: number;                // 同级手动排序
  createdAt: string;
}
```

**树的操作规则：**

| 场景 | 行为 |
|---|---|
| 删除一个有子节点的位置 | 子节点一并移入"未归位"？**不** —— 阻止删除，提示"请先处理 N 个子位置" |
| 删除一个存放了物品的位置 | 阻止删除，提示"该位置下有 N 件物品"，提供「全部移到…」快捷操作 |
| 移动位置 | 支持拖拽改父节点；**禁止把节点拖到自己的子孙下**（防成环） |
| 浏览某位置时 | 默认 **包含所有子孙节点的物品**（可开关切换为"仅本级"） |
| 空位置 | 位置树中用浅灰显示，一眼看出哪里是空的 |
| 未归位 | 虚拟节点，永远排在树顶，收纳所有 `locationId === null` 的物品 |

### 4.3 分类 Category 与标签 Tag

```ts
interface Category extends TreeItem {   // TreeItem: { id, name, parentId, order }
  createdAt: string;
}

interface Tag {
  name: string;                 // 标签名即主键，小写去空格归一化
  createdAt: string;
}
```

> **分类和位置一样是不限层级的树。** 可以做「化妆品 › 眼妆 › 眼影盘」这种结构，
> 物品**可以挂在任意层级**上 —— 有些东西你只想标成「化妆品」就够了，
> 没必要非塞进某个子类。
>
> 两者结构完全相同（都满足 `TreeItem`），所以树工具、路径匹配、合并算法
> 全部写成泛型由两边共用。共用一份的另一个好处是：防环、路径、子孙集合这些
> 容易出错的地方只需要正确一次。

**分类 与 标签 的分工（避免两者能力重叠造成困惑）：**

| | 分类 Category | 标签 Tag |
|---|---|---|
| 性质 | **受控词表**，你亲手维护的固定清单 | **自由输入**，随手打 |
| 结构 | **不限层级的树** | 扁平 |
| 一件物品 | 可属**多个**（用户选定），可挂在任意层级 | 可有多个 |
| 用途 | **"这是什么"** —— 统一按分类预览的主力 | **"情境标记"** —— 如 `想送人` `去年买的` `舍不得扔` |
| 界面位置 | 概览页图表、筛选器首位 | 筛选器次要位置，可折叠 |

**两条容易踩的规则：**

1. **重名只在同一级下算冲突。**「化妆品 › 眼妆」和「护肤 › 眼妆」
   是两个不同的分类，允许共存。但由此带来一个必须处理的副作用 ——
   AI 只说「眼妆」时无法判断该挂哪个，所以匹配规则里有一条：
   **有歧义就绝不猜**（见 16.6）。
2. **删除有内容的分类时，只处理直接层。** 直接子分类会被挂到顶层、
   直接挂在该分类上的物品会变成「未分类」，但**子分类里的物品不受影响**。
   位置树同理。这样删掉「化妆品」不会把「眼影盘」也弄丢归属。

## 5. 属性系统（"可自选加不加属性"）

这是需求里最特别的一点，单独成章。

### 5.1 属性定义

```ts
type AttrType = 'text' | 'number' | 'date' | 'select' | 'bool';

interface AttributeDef {
  id: string;
  name: string;                 // 如「品牌」「购入日期」
  type: AttrType;
  options: string[];            // 仅 select 用
  unit: string;                 // 仅 number 用，如「元」「cm」
  showByDefault: boolean;       // 录入时是否默认勾选
  order: number;
}
```

### 5.2 使用流程

```
① 在「管理 → 属性库」定义属性，例如：
     品牌(text) / 购入日期(date) / 价格(number,单位元) / 颜色(select:黑,白,灰,彩) / 是否常用(bool)

② 录入物品时，表单底部有一个「+ 添加属性」按钮
     → 弹出属性库清单，勾选这次要填哪几个
     → 勾选的才在表单里出现

③ 已保存的物品，可在详情页随时增删属性值

④ 浏览页可「按属性筛选」，例如：价格 > 500 且 颜色 = 黑
```

### 5.3 三个细节设计

1. **按分类记忆属性组合**：录入时若选了「衣物」，自动勾选你上次录衣物时用过的属性组合。
   避免每次都重新勾一遍。（否则这个设计会变成负担）
2. **属性库变更安全**：删除某个属性定义时，**不立即清除物品上的值**，而是提示
   "有 N 件物品使用了该属性，删除后这些值将不可见"，确认后才清理。删除前自动快照。
3. **空值不入库**：属性值清空后从 `attrs` 中移除该 key，保证导出数据干净。

## 6. 断舍离机制

### 6.1 物品状态机

```
        ┌──────────────┐
        │   active     │  在用
        │   在用       │
        └──┬────────┬──┘
           │        │ 标记闲置
   标记闲置 │        ↓
           │   ┌──────────────┐
           └──→│     idle     │  闲置 ← 独立的「闲置」页面汇总所有此类物品
               │   闲置       │
               └──┬────────┬──┘
                  │        │ 决定扔掉
        改回在用   │        ↓
                  │   ┌──────────────┐
                  └───│  discarded   │  已舍弃（软删除，可回顾/恢复）
                      │  已舍弃      │
                      └──────────────┘
```

### 6.2 「闲置」页面（用户明确要求的核心入口）

独立路由 `#/idle`，导航栏一级入口。

- 列出**所有** `status === 'idle'` 的物品
- 顶部统计：闲置 N 件 / 占全部 X%
- 每条显示：名称、位置路径、分类、**已闲置天数**（由 `idleAt` 计算）
- **按分类分组**（和物品列表页同一套分组样式与配色），组内按闲置时长**倒序** ——
  闲置最久的排最前，最该被扔的自动浮到顶
- 每条右侧两个操作：`改回在用` / `已处理（舍弃）`
- 支持多选 + 批量操作
- 全部处理完时显示一句"闲置已清空"，给一个正向反馈

> **为什么后来加了分组**：闲置的东西是散的 —— 衣服、电子、药品混在一条
> 按天数排的长队里，看的人得一件件回想「这堆是什么」。分成块之后，
> 一眼就能看出「原来闲置的主要是电子产品」，而「越久越靠前」这条规矩并没有丢，
> 它变成了**组内**的排序。分组复用物品列表页那一套（`.item-group` / `.group-head`、
> 同一份顶层配色表），所以两页的分组长得一样、同一个分类的颜色也一样。
>
> 两处刻意的差异：**闲置页的分组默认全部展开**（列表页默认折叠一级标题）——
> 这一页存在的意义就是从头看一遍，把东西折起来正好和这个目的作对；
> 但用户点过的折叠照样尊重，而且和列表页共用同一份展开状态。

### 6.3 已舍弃回收站

设置页内嵌，或独立 `#/discarded`。

- 列出已舍弃物品及舍弃时间
- 可 `恢复`（回到在用/闲置）或 `彻底删除`
- 彻底删除有二次确认

- **默认展开规则**：有子级的节点折叠，**叶子节点展开**。
  叶子下面没有结构可钻，折叠只会把内容藏起来、白点一次
- **展开状态会记住**（`ui.expandedGroups` / `ui.collapsedGroups`），所以只需要点一次
- 父级的件数是**含子孙的去重合计** —— 同一件东西挂在同一棵子树的两个节点上只算一次
- **一件东西都没有的分支不显示**，空分类不占地方
- 展开时先列子分类（结构），再列直接挂在这一层的东西

**平铺分组（标签 / 状态 / 不分组）**：本来就只有一层，默认展开。

## 8. 存储层设计

### 8.1 核心思路

数据量极小：**248 件物品的完整数据约 60KB**，即使 5000 件也只有 1MB 出头（无照片）。
所以**不做表结构，把整个 `AppData` 当作一个整体读写**。

好处链条：

```
全量整体读写
  ├─ 导出 = JSON.stringify(data)          → 零转换成本
  ├─ 导入 = 校验 + 写入                    → 零转换成本
  ├─ 快照 = 存一份副本                     → 零转换成本
  └─ 换后端 = 只替换 load()/save() 两个函数 → 业务代码零改动
```

### 8.2 Repository 接口（为 Supabase 预留的关键抽象）

```ts
interface Repository {
  load(): Promise<AppData | null>;
  save(data: AppData): Promise<void>;
}

class LocalRepository implements Repository { /* IndexedDB */ }
// v2:
// class SupabaseRepository implements Repository { /* 网络 */ }
```

业务层只依赖 `Repository` 接口，通过 `createRepository()` 工厂获取实例。
将来接 Supabase，改动范围仅限这一个文件。

### 8.3 IndexedDB 结构

```
数据库名: duansheli          版本: 1
  ├─ objectStore "app"        key: "data"  → AppData（全量数据，单条记录）
  ├─ objectStore "snapshots"  keyPath: "id", index: "at"  → 快照
  └─ objectStore "kv"         → 界面偏好、上次选择等小数据
```

`localStorage` 仅存一个 `duansheli:ui` 键，放界面偏好；**绝不用于主数据。**

### 8.4 自动快照策略

```ts
interface Snapshot {
  id: string;
  at: string;                   // ISO
  reason: 'auto' | 'import' | 'manual' | 'destructive';
  itemCount: number;
  data: AppData;                // 完整副本
}
```

**触发时机：**

| 时机 | reason | 说明 |
|---|---|---|
| 每次写入前 | `auto` | **同一分钟内只保留一份**（时间戳分桶，防止连续录入产生几十份快照） |
| 导入数据前 | `import` | 保证导入操作永远可回退 |
| 删除位置/分类/属性前 | `destructive` | 结构性破坏操作 |
| 用户手点「立即备份」 | `manual` | 设置页按钮 |

**保留策略：** 最多 30 份，超出后按时间淘汰最旧的。
但 `import` 和 `destructive` 类型的快照**优先保留**（至少各留 5 份）。

**UI：** 设置页显示快照时间线，可预览"这一份有多少件物品"，点「回退到此版本」。
回退前自动为当前状态再存一份快照 —— 所以**回退本身也可回退**。

## 9. 导出 / 导入

### 9.1 JSON 导出（主格式，用于备份与跨设备迁移）

```jsonc
{
  "format": "duansheli",          // 魔术字符串，导入时校验
  "schemaVersion": 2,             // v1→v2：分类从扁平变成树
  "exportedAt": "2025-01-15T10:30:00.000Z",
  "generator": "断舍离 v2",
  "summary": {                     // 便于人肉查看，导入时忽略
    "items": 248,
    "categories": 17,
    "locations": 17,
    "attributeDefs": 5
  },
  "data": {
    "items": [...],
    "categories": [...],          // 每条带 parentId（null = 顶层）
    "locations": [...],
    "attributeDefs": [...],
    "tags": [...]
  }
}
```

**版本号为什么要升：** 分类加了 `parentId` 是格式变化。
升到 v2 之后，**老版本的网页（比如手机上被 PWA 缓存住的旧版）拿到新备份会明确拒绝**
并提示升级，而不是静默把分类层级丢掉。反过来，v1 的老备份能正常导入 v2 程序，
那些分类会自动变成全是顶层。

文件名：`断舍离-备份-2025-01-15-1030.json`

### 9.2 CSV 导出（用于 Excel 查看，不可作为备份）

物品清单，UTF-8 **带 BOM**（否则 Excel 打开中文乱码）。

列：`名称, 数量, 状态, 分类, 位置路径, 标签, 备注, 创建时间, [各自定义属性列...]`

- 分类多值用 ` / ` 连接；位置输出完整路径 `家 / 卧室 / 衣柜 / 第二层`
- 自定义属性列动态生成，表头为属性名
- 值中含逗号、引号、换行时按 RFC 4180 加引号转义

**CSV 明确标注为"仅供查看，不能导入"** —— 避免用户误以为可以拿它恢复数据。

### 9.3 导入

**流程：**

```
选择文件
  → 解析 + 格式校验（魔术字符串、schemaVersion、字段类型）
  → 显示预览：「将导入 248 件物品、6 个分类、17 个位置」
  → 选择策略：覆盖 / 合并
  → 【自动为当前数据存一份 import 快照】
  → 执行写入
  → 显示结果报告
```

**校验失败时**给出明确原因（"这不是断舍离的备份文件" / "文件已损坏，JSON 解析失败"），
**绝不半途写入**（先全部校验通过再落盘）。

**两种策略：**

| | 覆盖 Replace | 合并 Merge |
|---|---|---|
| 行为 | 当前数据全部替换为导入数据 | 两边数据求并集 |
| 适用 | 换设备后恢复、找回旧版本 | 手机与电脑各自录了一半，想合起来 |
| id 冲突 | — | 保留 `updatedAt` 较新的那条 |
| 悬空引用 | — | 导入数据引用的位置/分类若本地不存在，**按名称路径尝试匹配**，匹配不到则**自动创建**（防止物品丢失归属） |
| 风险 | 低（有快照） | 中（可能产生重复项，导入后会提示"新增 X 项 / 更新 Y 项"） |

**推荐语：** 界面默认选中「覆盖」，因为对备份恢复场景它最可预期；
并附一句提示："如果你是想把两台设备的记录合起来，请选合并。"

## 10. 视觉规范

### 10.1 设计语言：白底 + 板块配色

> **⚠️ 这里改过一次。**
> 最初定的是「极简白 + 完全无彩色」，实际用起来太单调 —— 十二个板块长得一模一样，
> 换个页面几乎没有"我换地方了"的感觉。
> 现在改成：**底色、文字、线条仍然是中性的，但每个板块有自己的主色。**

**关键约定（改配色前先读）：导航栏本身保持中性灰。**

你任何时候看到的只有「当前板块」一种颜色。如果十二个板块在侧栏里各显各色，
那就是一道彩虹，反而更乱。颜色只出现在**你正在看的那一屏**上。

```
导航项（未选中）  →  中性灰
导航项（选中）    →  该板块的 accent-soft 底色 + accent-text 文字 + accent 左侧竖条
页面内容         →  全部使用当前板块的 accent
```

### 10.2 十二个板块的主色

| 板块 | 主色 accent | 文字色 accentText | 浅底色 accentSoft |
|---|---|---|---|
| 概览 | `#2563eb` 蓝 | `#1d4ed8` | `#eff6ff` |
| 物品 | `#4f46e5` 靛 | `#4338ca` | `#eef2ff` |
| 位置 | `#0d9488` 青绿 | `#0f766e` | `#f0fdfa` |
| 闲置 | `#d97706` 琥珀 | `#b45309` | `#fffbeb` |
| AI 助手 | `#7c3aed` 紫 | `#6d28d9` | `#f5f3ff` |
| 分类 | `#0891b2` 青 | `#0e7490` | `#ecfeff` |
| 属性 | `#059669` 翠 | `#047857` | `#ecfdf5` |
| 标签 | `#db2777` 玫红 | `#be185d` | `#fdf2f8` |
| 设置 | `#475569` 石板 | `#334155` | `#f8fafc` |

三个色阶的用途：

- **accent** —— 按钮底色、图表、激活态、开关、复选框
- **accentText** —— 在白底上直接当文字用（比主色深一档，保证对比度）
- **accentSoft** —— 激活项背景、输入框聚焦光晕、提示块底色

实现在 `src/lib/sections.ts`。**板块主色被写到 `:root` 上，而不是写在某个容器上** ——
因为模态框和轻提示是通过 `createPortal` 挂到 `document.body` 的，
写在容器上它们就继承不到颜色（这个坑很容易踩）。

### 10.3 中性底子（不随板块变化）

```
背景
  --bg          #ffffff      页面底
  --bg-sub      #fafafa      次级区块
  --bg-hover    #f4f4f3      悬停态

线条
  --line        #e8e8e6      1px 分割线
  --line-strong #d4d4d1      边框、输入框

文字（三级即可，不再多）
  --text        #1a1a1a
  --text-2      #6b6b6b
  --text-3      #9b9b9b

唯一固定不随板块变的彩色
  --danger      #b3261e      只用于「彻底删除」这类不可逆操作的文字，绝不做按钮底色

中性灰阶（只留给少数「不该带颜色」的地方：轻提示底色、开关滑轨）
  --fill-1      #1a1a1a
  --fill-4      #e0e0e0
```

**规则：**
- ❌ 不用渐变、不用阴影表达层级（唯一例外：手机悬浮按钮 + 深色浮层）
- ❌ 不用彩色图标做装饰 —— 图标跟随 `currentColor`
- ✅ 用 1px 细线划分区块，用字号 / 字重 / 灰度差表达层级
- ✅ 颜色只用来**标识板块**和**指示可操作**，不用来表达"重要性"

### 10.4 数据配色：分组一种颜色

板块主色是**界面色**（按钮、激活项这些"壳"），分组色是**数据色**（分类、位置这些"内容"）。
两套并存，互不冲突。

物品列表按分类 / 位置 / 标签分组时，每组一个颜色：

```
▌● 衣物                    68 件
├──────────────────────────────
│  灰色羊毛衫     卧室/衣柜
│  牛仔裤         卧室/衣柜
▌● 电子                    41 件
│  旧手机         床头柜
```

**树形分组（分类 / 位置）时还会嵌套**，子分组渲染在父分组的框里 ——
父级那条彩色竖条就把整棵子树括起来了：

```
▌▶ 化妆品                  38 件
│  ▌▶ 眼妆                 12 件
│  │  ▌● 眼影盘……
│  ▌▶ 唇妆                  9 件
```

- 整组一条 **3px 彩色竖条**（`border-left`）
- 标题行：**折叠箭头 + 色点 + 同色标题文字 + 极浅同色底**
- 组内分隔线用同色系的浅色，把整组"框"起来

**条形图也用同一套颜色**，这样图表里的「化妆品」和列表里那一组颜色对得上，
一眼能连起来。

#### 四条分配规则

| 规则 | 为什么 |
|---|---|
| **同一个 key 永远同一个颜色**（由 key 哈希决定，不按顺序） | 「衣物」不论在哪个筛选、哪个排序下都是同一个颜色，你能靠颜色认东西，而不是每换一次视角就重新学一遍 |
| **尽量不重复**（同一份 key 列表里一个颜色只用一次） | 色板 12 个色，分组通常不到 12 个，那就该做到全不重样 —— 隔一组撞色同样让人分不清 |
| **相邻要把色相拉开 ≥28°**（不只是色值不同） | 色板里有三个绿、两个橙、两个红；光挡"色值相同"不够，挨着的一个绿一个青绿看起来照样像同一组 |
| **虚拟分组一律中性灰**（未分类 / 未归位 / 未加标签 / 全部 / 其他） | 它们是"没有值"，不该跟真实分类抢眼 |

状态分组（在用 / 闲置 / 已舍弃）不用哈希，走固定的语义色 ——
含义是固定的，"在用"就该是绿的、"闲置"就该跟「闲置」板块一样是琥珀色。

配色表在 `src/lib/palette.ts`，12 色都取同一档明度（600 / 700 / 50 / 200），
摆在一起色感统一，不会花。

#### 第 5 条：树形分组**只在顶层上色**（后加的，重要）

第一版的树形分组是**每个节点各自哈希**，结果是：一个一级标题下面，
子分类各是各的颜色，一块里面五彩斑斓。用户的原话是「太五颜六色了」。

问题在于颜色的**职责**被用错了地方：它本来是用来「把大块分开」的，
用在同一块的**内部**只会添乱 —— 同一块里的东西本来就已经挨在一起了，
再用五种颜色去标，读的人反而要多花力气去猜「这几个颜色是什么关系」。

现在改成：

| 表达什么 | 靠什么 |
|---|---|
| 这是哪一大块 | **颜色**（只有顶层拿独立色相） |
| 属于哪一层 | **缩进** |
| 离顶层多远 | **深浅**（竖条 / 色点 / 底色 / 分隔线逐层变淡） |

```
▌▶ 化妆品                  38 件     ← 青色，最实的竖条
│  ▌▶ 眼妆                 12 件     ← 同一个青色，混白 45%
│  │  ▌▶ 眼影                6 件     ← 再浅一档
│  ▌▶ 唇妆                  9 件     ← 和眼妆同档（同层同色）
```

两个细节：

- **文字颜色不变**，只让竖条 / 色点 / 底色 / 分隔线变淡。
  小字号再往浅里混，对比度会掉到看不清（白底上混掉 40% 就低于 4.5:1 了）；
  而且标题文字用同一个色相，反而强化了「你还在化妆品这一块里」的感觉。
- **只分两档**（第一层 / 第二层及更深）。再深的层级缩进已经很明显，
  继续变淡会让第四层几乎只剩白色。

#### 一个必须小心的连带问题：图表和列表的颜色要对得上

上面第 2、3 条规则都**依赖整个 key 列表**（不重复、相邻拉开），
于是「同一批 key，但列表不同」就会算出不同结果。而现实里两边天生不同：

- 物品列表只渲染**有内容的**分组
- 概览图表只画**有数量的**分类

所以顶层颜色必须从**同一份规范 key 列表**（完整的顶层节点，按树里的显示顺序）
算出一张表，两边都查这张表（`topLevelColorMap` → `assignTreeColors(roots, topColors)`
/ `BarChart` 的 `colorOf`）。否则会出现「列表里化妆品是蓝的、图表里是绿的」。`

### 10.5 尺度

```
圆角    8px（卡片/输入框）  4px（小标签）
间距    8 / 12 / 16 / 24 / 32 / 48（4 的倍数）
```

### 实现时的一处调整

M4 原计划用**拖拽**移动位置。实际改成「选中节点 → 点『移动到…』→ 在树里挑新父节点」，
原因有两个：

1. **HTML5 拖放事件在触屏设备上根本不触发**，手机上会用不了 —— 而手机是主要使用场景之一。
2. 用现成的位置选择器顺带复用，代码更少，也不会出现「拖歪了」的误操作。

防环逻辑（`canReparent`）保持不变，仍然禁止把节点移到自己的子孙下。

> **后来的补充**：位置拖拽一直没做，但**物品**拖到位置上做了 ——
> 两者代价不同，理由见第 30 节。

## 13. 已知限制（如实记录）

1. **手机与电脑数据不互通**（v1），靠手动导出/导入。v2 接 Supabase 解决。
2. **浏览器数据可能被清除** → 必须定期点「导出 JSON」存到网盘或本地。README 会重点标注。
3. **换域名（如绑自定义域名）会导致旧 origin 数据"看不见"** → 换之前先导出。
4. **不做照片** → 无法凭图认物，需依赖名称。建议名称写得具体（如"灰色羊毛衫"而非"毛衣"）。
5. **CSV 只能导出不能导入**（信息有损）。
6. **合并导入可能产生重复项**，导入后会提示新增/更新条数，需人工核对。

| 双语：没有东西被冻住 | 7 | 状态名/相对时间/日期/数字/种子脚手架/有效期分组名**切语言后都真的变**；配色不受语言影响 |
| 双语：选择与持久化 | 5 | 写 localStorage 并读回、同语言不重复通知、`<html lang>`、locale 映射、语言不自称翻译 |

| 清单：从物品或活动建 | 4 | 条目是**快照**（物品改名不影响它）、只收勾选的那几件、记下来源、删掉活动后清单不受影响 |
| 清单：打钩与编辑 | 6 | 打钩与取消、可显式指定状态（供「全部取消」用）、**就地改名改数量不动库里的物品**、空名字被拒、可加库里没有的条目、清掉已打钩的 |
| 清单：删除与导入导出 | 4 | 删整份清单时物品与活动都不受影响、打钩状态一起往返、老备份缺字段补空、**坏一条只跳那一条不整份丢**、合并时撞 id 整份保留本地那份 |
| 数据体检 | 15 | 四种结论分得清（数据在 / 可恢复 / 这个网址没有 / 读不出来）；**读失败绝不许伪装成「没有快照」**；只剩空快照时不说「能找回」；并列快照取更新的那份；体检**只读**（跑三次快照数不变）且**绝不读 API Key 的值** |
| AI 会话：跨页面活着 | 12 | 切页面回来对话与草稿都还在（渲染层面那 2 条在「渲染冒烟」组里，**真的点「新对话」按钮走一遍确认框**）；会话**不落盘**（localStorage / kv 表 / 主记录里都搜不到）；数据整体替换时作废、合并导入与删一件物品时**不许**作废 |
| AI 认不认识工具的词汇 | 28 | 状态词（中文/英文/代码值/中文键名）都解析得出；**且「没提到」和「在用」必须分开**；`spare` 进得了 loadScope；**只改状态也算改动**（变异验证过）；AI 说「已舍弃」转成一次可恢复的删除；活动只认已有的、对不上的如实报告；概念表整段进了抽取和对话两个 system |
| 备用：拆出备用与取用 | 20 | **数量守恒**（拆分前后总件数不变）；原处一定留 1 件；`tooFew` / `discarded` / `notFound` 三种拒绝各自不改动数据；取用**恰好**进出 1 件、最后一件才变「在用」、**绝不进回收站**；备用不进闲置统计；spare 能原样往返备份；认不出的状态退回「在用」而不是丢掉整条 |

测试**不覆盖网络请求本身** —— 那是在测 DeepSeek，不是测这个项目。

### 三个值得记下来的技术坑

**1. zustand 在服务端渲染时读的是初始状态。**
`useStore` 传给 `useSyncExternalStore` 的 server snapshot 是
`api.getServerState || api.getInitialState` —— 也就是 store **创建那一刻**的状态。
所以用 `react-dom/server` 做测试时，`setState` 完全不起作用，页面永远渲染成空数据。
这就是渲染测试必须用 `jsdom` + `createRoot` 而不是 `renderToString` 的原因。

**2. jsdom 没有 `attachEvent` / `detachEvent`。**
React 的 input 事件兜底逻辑在元素获得焦点时会调用 `activeElement.detachEvent(...)`，
jsdom 缺这两个方法就会抛 `TypeError`。在 `tests/dom.ts` 里补一对空实现即可。

**3. 名称匹配里的「聪明」是危险的。**
最初的位置匹配写成了「完整路径对不上，就退回按末级名称找」。
测试立刻抓到一个真实事故场景：AI 说「家 / 车库 / 货架」，而用户树里另有一处
「家 / 储物间 / 货架」—— 于是东西被悄悄挪进了储物间。
现在改成：**只有 AI 只给了单独一个名字时才按名称匹配**，
给了完整路径却对不上就一律标成「新位置」，交给用户决定。
这类 bug 的可怕之处在于它不会报错，你只会在很久以后发现东西不在它该在的地方。

## 16. AI 功能（DeepSeek 接入）

### 16.1 定位

手工录 200 件东西是很枯燥的事。AI 功能解决的就是**录入的启动成本**：
把一段随手写的文字变成录好的物品，并自动对齐到你已有的分类和位置上。

**它不是「替你决定」，而是「替你打草稿」。** 所有结果先进预览，你过一遍才写入。

### 16.2 前提：浏览器能不能直连（已实测）

这是整个方案的生死线。如果 DeepSeek 不返回 CORS 头，纯静态站就只剩两条路：
自建代理服务器（违背"纯静态 + 零运维"），或者用第三方代理（**Key 必然经过别人的服务器**，
直接违背用户"Key 必须存在本地"的硬要求）。

不能靠搜资料猜（网上说法互相矛盾），所以写了 `scripts/probe-deepseek-cors.mjs` 实测：

```
=== 预检 OPTIONS ===
HTTP 状态： 200
✅ access-control-allow-origin: https://example.github.io
✅ access-control-allow-headers: authorization,content-type
✅ access-control-allow-methods: POST

=== 实际 POST（假 Key） ===
HTTP 状态： 401
✅ access-control-allow-origin: https://example.github.io
```

结论：**允许浏览器直连**。请求从你的浏览器直达 `api.deepseek.com`，
不经过任何第三方。这个脚本保留在项目里 —— DeepSeek 将来若改策略，跑一下就知道。

### 16.3 API Key 的存放：存本地，但不外泄

> **⚠️ 这里改过一次。**
> 最初定的是「只存内存、刷新即清空」，理由是下面那两个风险。
> 实际用起来每次都要粘贴一次，太烦 —— 用户明确要求改成存本地（"我可以手动自己清除"）。
>
> 改动之后，**页面上的「清除」按钮和风险提示就变成了必须品**，
> 而不是可选的好看装饰。这一点不能含糊。

**Key 存在 `localStorage` 的 `duansheli:ai-key` 键上。**

刻意跟界面偏好（`duansheli:ui`）分开用独立的键，好处有两个：

- 清界面偏好不会连 Key 一起清掉，反过来也一样
- 想手动删的时候，在浏览器存储里搜 `duansheli` 就能找到它

**它绝不会去的地方：**

| 位置 | 为什么不行 |
|---|---|
| 导出的备份文件 | 备份是要拿去传网盘、换设备的，等于把钥匙一起带走 |
| IndexedDB | 那里存的是用户的物品数据，不该混进凭据 |

这两条有测试守着 —— `tests/ai.ts` 的「API Key：存在本地，但不外泄」一组，
还额外断言了**全站只有 `duansheli:ai-key` 这一个键包含 Key**，
免得将来某个改动不小心把它复制到别处。

```ts
export interface AppState {
  /** 保存在这台设备的 localStorage 里；传 '' 表示清除 */
  aiApiKey: string
  setAiApiKey: (key: string) => void
}
```

注意它挂在 store 顶层而**不是** `data` 里 —— 导出的只是 `data`，
所以从数据结构上就不可能被带出去。

**必须如实告诉用户的两个风险（纯前端无法消除）：**

1. 任何能在你浏览器上执行 JS 的代码理论上都能读到它（恶意插件、XSS）。
2. **浏览器存储按域名隔离，而 `用户名.github.io` 是所有仓库共享同一个域名的。**
   如果你将来在同一账号下部署别的项目，**那个项目的页面能读到这个 Key**。

界面上建议单独建一个只用于这里的 Key，方便随时吊销。

### 16.4 一个对话框（三合一）

> **⚠️ 这里合并过一次。**
> 最初拆成了三个模式：**一次性录入 / 对话整理 / 整理已有物品**。
> 那是**实现上的边界漏到了界面上** —— "新建"和"更新"是我代码里的两条路径，
> 不是用户会关心的事。
>
> 用户实际用的时候立刻就撞墙了：他在对话框里说「把现在的药品改成 药品/补剂」，
> 那是再自然不过的一句话，但对话框**结构上就够不着数据库** ——
> 它只认一份空的待录入草稿。
>
> 而「整理已有物品」那个模式也确实没用：它是批处理式的，
> AI 建议完只能全盘接受或放弃，**想让它改一下都不行**。
>
> 所以三个合成一个。

```
用户说一句话（要录新的，或者要改现有的）
   ↓ 请求 = [system: 角色规则 + 用户体系 + 现有物品目录] + [历史] + [草稿 + 指令]
   ↓ AI 可能回：
       · items / removedIds   → 正常的新增与修改
       · loadScope            → "我需要先看看你现有的物品"，程序自动拉进草稿并再问它一轮
       · 只有 reply           → 纯问答，草稿不动
   ↓ 按 id 合并进草稿
右侧草稿实时更新，改动的那几条高亮
   ↓ 用户继续用大白话让它改，或者点「采纳」
```

#### 草稿里混着两种东西，采纳时自动分流

| 草稿条目 | 来源 | 采纳时 |
|---|---|---|
| 带 `sourceItemId` | 从数据库拉进来的现有物品 | **更新**那一条 |
| 不带 | 这次新录入的 | **创建**一条新的 |

用户不需要知道区别 —— 界面上只用一个小标签标出「已有」，
并在按钮上写清「更新 74 · 新建 3」。

**一个容易踩的坑：** `mergeChatResponse` 更新草稿时必须把 `sourceItemId` 一起带过去。
丢了它，采纳时就会把这些已有物品当成新条目**又建一遍**。这条有专门的测试守着。

另一个：**内容没变的已有物品要跳过**。把 74 件药品拉进来只改了 3 件，
如果采纳时把 74 件都写一遍，它们的修改时间全被刷新，排序和「最近修改」就全乱了。

删除的边界：被移出草稿的已有物品 → **移入回收站**（可恢复），不是硬删。

#### 现有物品怎么到 AI 手里（省 token 的关键）

不能把用户全部物品塞进 prompt —— 500 件就是一万多 token，每轮都发。

**分层解决：**

1. **system 里只放「目录」**：每个分类 / 位置有多少件，几百 token 而已。
   因为放在 system 里、前缀稳定，还能命中缓存。
2. **AI 真需要具体条目时，用 `loadScope` 主动要**：

```jsonc
{
  "reply": "你「药品」下有 74 件，我先拉进来看看",
  "loadScope": { "categoryPaths": [["药品"]] }
}
```

   程序收到后把对应物品放进草稿，**自动再问 AI 一轮**（最多 3 轮，防死循环）。
   那一轮 AI 就能看到具体条目，按正常方式改。

`loadScope` 支持 `all` / `idle` / `uncategorized` / `unassigned` /
`categoryPaths` / `locationPaths`，几种条件取并集。

于是用户的体验就是：**说一句话，它自己去找要动的东西。** 中间那步看得见但不用管。

#### 三条安全底线

这是整个功能里最容易写错的地方 —— 让 AI 反复改一份草稿，
稍不注意就会丢东西。所以定了三条硬规则：

1. **AI 每轮只返回改动过的条目，没提到的一律原样保留。**
   这比「要求它返回完整列表」既更安全也更省 token：语义上「没提到」= 「不用动」，
   不再有「AI 是忘了写还是想删掉」的歧义。
   删除只能由 AI 显式放进 `removedIds` 触发，而且只有**确实存在于数据库里**的 key 才作数 ——
   AI 编出来的 id 一律忽略。
2. **改动要能被看见。** 合并时对每条算一个内容指纹（名称 + 数量 + 分类路径 + 位置 +
   标签 + 属性 + 备注），指纹变了就在草稿行上加亮。
3. **永远不自动写入。** 只有用户点「采纳」才会 commit；
   删除是**软删除进回收站**，还能捞回来。

还有一个细节：**用户手动做过的选择（取消勾选、采纳了新分类）在 AI 改内容后要保留**，
不能因为 AI 改了名字就把用户勾掉的东西又打开。

### 16.5 Prompt 设计要点

1. **注入用户自己的词表。** 把已有的分类清单、**完整位置路径**、属性名一起发过去，
   并明确要求优先复用。这一步直接决定结果能不能对得上现有数据。
2. **明确禁止猜测。** "原文没有提到位置就填 null —— 不要猜、不要编。"
   宁可让它留空，也不要它编一个看起来合理的位置。
3. **允许但约束新分类。** "确实没有合适的，才写一个新分类名。名字要短、要通用
   （「户外装备」可以，「乱七八糟的东西」不行）。"
4. **区分分类与标签。** 分类回答"是什么"，标签回答"什么情境"。
5. **必须出现 "json" 字样** —— 这是 DeepSeek JSON 模式的要求，不满足会直接报错。
6. **属性 key 只能来自已有属性名**，本地不存在的在转换层会被丢弃并在界面如实告知。

### 16.6 匹配规则：保守优先

AI 给的是名称路径，数据库存的是 id。中间这层匹配是最容易出隐蔽错误的地方。
**分类和位置都是树，用的是同一套规则。**

**核心原则：宁可标成"新建"让用户决定，也不要猜。**

```
AI 说「家 / 车库 / 货架」，用户树里只有「家 / 储物间 / 货架」
        ↓
❌ 按末级名称「货架」匹配  →  东西被悄悄挪进储物间（不报错，你很久以后才发现）
✅ 标成「新位置」，默认不勾选  →  用户自己决定
```

三级降级：

1. **完整路径精确匹配** → 用
2. **把 AI 给的路径当作已有路径的后缀匹配** —— 但**只在后缀唯一时才用**。
   AI 只给「眼妆」而全树只有一处叫「眼妆」，能对上；
   AI 给「卧室 / 衣柜」而完整路径是「家 / 卧室 / 衣柜」，也能对上。
3. 其余 → 标记为新分类 / 新位置，默认不勾选

> 第 2 条的限制是测试抓出来的：最初的实现无脑按末级名称匹配，
> `tests/ai.ts` 里「危险的同名跨分支必须不匹配」这条用例直接把它钉死了。
>
> 分类支持多级之后，歧义场景变得更容易出现 ——
> 「化妆品 › 眼妆」和「护肤 › 眼妆」可以共存，
> 这时 AI 只说「眼妆」就必须判为歧义、**不猜**。这条也补了专门的测试。

跨设备合并导入用的是另一套规则（按名称路径**自动补建**），因为那是用户自己数据的迁移，
丢掉归属的代价更大。两处的取舍不同是有意的。

### 16.7 分批策略

一次塞太长的输入，输出的 JSON 会因 `max_tokens` 被截断 ——
而**截断的 JSON 是解析不了的**。用户会以为"AI 认不出来"，其实是结果被砍了后半截。

所以：
- 输入按**段落边界**切成每批约 2500 字（`splitIntoChunks`），超长单行硬切
- 检测 `finish_reason === 'length'`，命中时明确提示"这一批被截断了，建议拆小一点"
- `max_tokens` 给到 8192
- 界面上显示"正在识别第 2 / 5 批"和累计 token

`splitIntoChunks` 有测试保证切分后拼回来内容不丢、超长单行不死循环。

### 16.8 错误处理

`AiError` 带一个 `kind` 和一句**告诉用户该怎么办**的中文：

| 情况 | 提示 |
|---|---|
| 401 | Key 无效，检查是否复制完整、是否过期 |
| 402 | 余额不足，去开放平台充值 |
| 429 | 请求太频繁，等一会儿 |
| 500/502/503 | DeepSeek 服务端暂时出问题 |
| 网络失败 | 连不上，检查网络 / 广告拦截插件 |
| 返回空内容 | JSON 模式的已知偶发情况，直接再点一次 |
| 解析不出 JSON | 错误信息里附带原文开头 120 字，方便判断 |

界面上显示 key 状态、进度、token 消耗，运行中有「取消」按钮（`AbortController`），
请求有 180 秒超时。

### 16.9 明确不做

- ❌ **不自动写入。** 预览这一步是硬性的，没有"一键直接入库"的开关 ——
  对话模式同样如此，必须用户点「采纳」。
- ❌ **不让 AI 自动创建分类。** 分类是受控词表，必须逐个确认。
- ❌ **不让 AI 自动创建属性定义。** 只填已有属性，不认识就丢掉并告知。
- ❌ **不在界面上写死价格。** 官方调过几次价，写死的数字迟早骗人。
  改为显示实际消耗的 token 数（输入/输出分开），用户自己乘单价。
- ❌ **不做自由聊天。** 对话模式是**围绕一份草稿**的，不是通用聊天机器人。
  没有草稿就没有意义 —— 所以第一轮的输入是待录入的描述，之后就都是修改指令。
  这跟"陪聊"是两回事，也避免了把 token 花在无关的闲聊上。

> **改过一次的地方：** 最初这里写的是"不做多轮对话式录入"。
> 后来用户实际用的时候撞上了一个真实场景 —— AI 把口红归进了「日用品」，
> 而他除了重新粘一遍原文之外**没有任何办法纠正**。
> 这才意识到"一次输入一次输出"漏掉了最重要的一环：**改**。
> 于是补上了对话模式，但保留了"草稿 + 采纳"的核心结构，而不是放任成自由聊天。

## 17. 省 token 的做法

对话模式每轮都要重发不少东西，所以专门优化过。三处，按收益排序：

### 17.1 AI 只返回改动过的条目（最大头）

见 16.4 的说明。33 条物品时，每轮输出从 **2500+ tokens 降到几十**。

### 17.2 用户体系放进 system 消息，而不是每轮的用户消息

DeepSeek（和多数推理服务）有**前缀缓存**：请求开头那段如果和上一轮逐字节相同，
命中的部分按缓存价计费，比正常输入便宜很多。

```
请求结构：
  [system: 角色规则 + 已有分类/位置/属性/标签]   ← 稳定，命中缓存
  [历史对话]                                     ← 只追加，前缀不变
  [当前草稿 + 用户指令]                           ← 每次都不一样（结尾）
```

关键就是**把稳定的东西放在最前面**。最初把用户体系放在每轮的用户消息里，
那它就在请求**结尾**，永远命中不了缓存 —— 白白多花钱。

有测试守着这一条：断言两轮的 system 消息**逐字节一致**，
并且用户消息里不再重复一遍体系。

### 17.3 空字段不发出去

一整批物品里，大部分条目没有标签、没有属性、没有备注、没有位置。
这些字段全发一遍很浪费：

```jsonc
// 改前
{ "id": "a", "name": "一张纸", "quantity": 1,
  "categories": [], "location": null, "tags": [], "attributes": {}, "note": "" }

// 改后
{ "id": "a", "name": "一张纸" }
```

缺省值由解析层负责补回来（数量默认 1、其余默认空），所以不会丢信息。

### 17.4 顺带做的两件小事

- **历史只留最近 8 条消息。** 草稿本身就是完整状态，历史主要用来理解
  「刚才那个」这类指代，留太长每轮都要重发，纯粹烧钱。
- **界面上显示 token。** 聊天面板顶部显示「上轮 N · 共 M」——
  用户能看出这轮贵不贵，自己决定要不要开新对话。

### 17.5 给用户的建议（写在界面上）

> 改完一批就点「采纳」，然后开个「新对话」——
> 对话越长、草稿越大，每轮要重发的内容也越多。

「新对话」按钮带二次确认，因为草稿还没入库，关掉就真没了。

## 18. 有效期（过期时间）

### 18.1 定位

给药品、化妆品、食品这类**有保质期**的东西记一个到期日，然后有一个地方能一眼看到
「哪些已经过期 / 哪些快过期了」。它是「断舍离」这条主线的补充：
闲置告诉你「你多久没动它了」，有效期告诉你「它自己快不行了」。

### 18.2 三条设计决定

**一、只存日期，不存时间点。** `expiresAt` 是 `YYYY-MM-DD`，比较时两边都取本地日的 00:00。

如果存时间点会很难受：`2026-03-15T00:00:00Z` 在东八区其实是 3 月 15 日早上 8 点，
而「今天到期」过了本地零点就该变成「已过期 1 天」—— 带时分秒之后这个边界永远算不清。
只留日期，语义就是「那一天结束前」，「今天到期」永远是 0 天。

顺带一个坑要专门挡：归一化时**不能** `new Date(x)` 再取本地日期。
`2026-03-15T23:00:00.000Z` 在东八区会变成 16 号，用户会莫名多一天。
所以是字符串截取到 `T` 之前，不经过时区。这条有专门的用例守着。

**二、到期不改任何数据。** 没有定时任务、没有自动标闲置、没有自动进回收站。
过期是个**每次渲染现算的状态**（`expiryState`）。

理由：如果到期就自动把东西标成闲置，用户哪天觉得它还能用，数据已经被悄悄动过了 ——
这和整个项目「只有你点了才写入」的原则直接冲突。
一个提醒功能不该有副作用。

**三、没设置 ≠ 已过期。** 四档状态里 `none` 和 `ok` 是分开的，
而且界面上**给「没填」不显示任何徽章**。
如果给没填的也画个灰色小标签，一屏看过去全是标签，真正要紧的那几条反而被淹掉了。

### 18.3 四档与可调阈值

```
expired  已过期         红（全站唯一一处「重」提示）
soon     N 天以内到期    琥珀
ok       还早            灰色小字
none     没设置          什么都不显示
```

**N 可调（默认 30）**，存在界面偏好里。这是个必须做成可调的数：
鲜奶的「快到期」是 3 天，化妆品是半年，写死一个值必然对一半人没用。

### 18.4 放在哪

- **独立页面 `/expiry`**：按四档分组，已过期在最上；阈值选择器在顶部；支持批量清日期 / 舍弃
- **物品行徽章**：`已过期 200 天` / `还有 12 天`。共用 `ExpiryBadge`，阈值从 store 读
- **录入表单**：日期选择器 + 清除 + 四个快捷按钮（一周/一月/半年/一年后）
- **概览卡片**：有东西要到期时才出现，点进有效期页
- **筛选与分组**：筛选面板多一组「有效期」，分组维度多一个「按有效期」
- **排序**：多一个「按有效期」，**没填日期的固定排在最后**（用 `compareExpiry`，
  它不乘方向符号 —— 否则倒序时一大片没填的会浮到最前面，把要紧的冲散）
- **CSV**：多一列「有效期至」，没填是空格子（不写「—」，表格软件里空着才好排序筛选）
- **AI**：能填（「这盒药 2026 年 3 月过期」）、能查（`loadScope` 新增
  `expiring` / `expired` / `hasExpiry` 三个范围）

### 18.5 一处最危险的实现细节

草稿和库里的物品之间有一个「内容指纹」比较，指纹没变就跳过不写（省得白刷 `updatedAt`）。

**`expiresAt` 必须进这个指纹。** 漏了会出这种事：AI 只帮你补了有效期，
指纹没变 → 判定「没改动」→ 跳过 → 你看到 AI 说改好了、采纳后却什么也没发生。
改动凭空消失，而且完全无声。

`effectiveSignable`（草稿侧）和 `itemSignature`（库侧）两个指纹函数都加了它，
并且有一条专门的用例：**只改有效期，必须判为「有改动」**。

### 18.6 数据版本

`SCHEMA_VERSION` 2 → 3。
升版本是为了保护老程序：它拿到更高版本的备份会**明确拒绝**并提示升级，
而不是静默把不认识的 `expiresAt` 丢掉 —— 静默丢字段是最糟的，用户会以为备份是完整的。
反过来老备份能正常导入，缺的字段读出来是 `null`，不需要额外迁移逻辑。

单条记录里的坏日期（比如 `2025-02-30`）只把那一条归成 `null`，**不拒绝整份文件** ——
一条数据不该让用户几百件东西都导不进来。

## 19. 中英双语

### 19.1 一句话原则

**界面文字要翻，用户录入的内容一个字都不翻。**

「你建的分类叫『化妆品』」和「界面上那个按钮叫『保存』」是两回事。
前者是数据，切了语言它还是「化妆品」；后者是文案，该变。
这条边界有测试守着（英文界面下断言物品名仍是中文），也是最容易做错的地方。

推论：**首次启动铺的脚手架**（`家 / 卧室 / 衣柜`、`衣物 / 电子`）是**数据**，
所以它按**首次启动时的界面语言**生成一次，之后切语言不会去改它。
否则你精心改过的分类名会被悄悄翻译掉。

### 19.2 为什么不装 i18next

整个项目只有 4 个运行时依赖，这是刻意维持的。这里真正需要的只有：
一份字典、一个查表、一个插值、一个「切换了要重新渲染」的通知。自己写约 250 行，
读起来还更直白，也不用担心某个库的复数规则和我们想的不一样。

### 19.3 关键设计：让编译器盯着双语别漂

```
src/i18n/
  index.ts        运行时：语言状态、t / tc、useT、Intl 封装
  zh/index.ts     中文词典的聚合，**同时定义类型**（唯一真源）
  zh/<区域>.ts    一个界面区域一个文件（common / nav / items / ai / ...）
  en/index.ts     英文词典的聚合
  en/<区域>.ts    与 zh 一一对应
```

`en` 的类型被写成 `Dict = typeof zh`：

```ts
// src/i18n/en/index.ts
export const en: Dict = { common, nav, status, ... }
```

于是「英文少写了一个 key」**直接编译不过**，多写一个也过不去（对象字面量的多余属性检查）。
双语不同步是这类项目最常见的腐烂方式，让 `tsc` 替我们盯着，比靠人记得可靠得多。

⚠️ **代价：字典里不能写 `as const`。** 加了它值会变成字面量类型（`'保存'` 而不是 `string`），
英文永远没法满足 `typeof zh`，约束当场失效。这条写在 `docs/i18n-约定.md` 里。

### 19.4 语言是模块级状态，不是 React Context

因为**一大半文案在 React 之外**：store 里的 toast、导入校验的报错、
API 客户端的错误映射、种子数据的生成。那些地方拿不到 context。

所以语言是个模块级变量，组件通过 `useSyncExternalStore` 订阅它：

```ts
export function useT() {
  const lang = useLang()               // useSyncExternalStore
  return useMemo(() => ({ t, tc, lang }), [lang])
}
```

`useT()` 不只是给你 `t`，它同时负责**订阅** —— 漏了它的组件切了语言不会重渲染，
界面上就留下半截中文。这类 bug 只在真实 DOM 里看得出来，所以专门有一条
「英文下把 15 个页面各挂一遍」的渲染测试。

### 19.5 第二危险的坑：模块加载那一刻被冻住

```ts
// ❌ 看着没问题，其实是坏的
export const STATUS_LABEL = { active: t('status.active'), ... }

// ✅ 每次调用时求值
export function statusLabel(s: ItemStatus) { ... }
```

模块顶层的 `t()` 会在**模块加载那一刻**把当时的语言冻在里面，之后怎么切都不变。
症状很隐蔽：大部分文字变了，就这一处没变。

审计时发现并改掉了两处这种模式（`STATUS_LABEL`、`Attributes.tsx` 里的属性类型名表）。
现在测试里有一组「切语言后各处必须真的跟着变」的用例专门盯着它，
覆盖状态名、相对时间、日期、数字、种子脚手架、有效期分组名。

### 19.6 单复数：中文那两条写一样的话

英文要区分 `1 item` / `3 items`，中文不用。处理方式是词干 + `_one` / `_other`：

```ts
// zh:  countItems_one: '{count} 件',  countItems_other: '{count} 件'
// en:  countItems_one: '{count} item', countItems_other: '{count} items'
tc(3, 'format.countItems')   // → 「3 件」/「3 items」
```

中文那两条写一样的话，看着冗余 —— 但换来的是**两份字典形状完全一致**，
而形状一致正是 19.3 那套类型约束能成立的前提。这比省几个字值钱。

`tc` 的词干也有类型约束：`tc(3, 'format.countItems')` 里拼错的词干编译不过。

### 19.7 日期与数字

- `2025-01-15` 这种格式**两种语言都用，不做本地化**：没有歧义，而且按字符串排序就是按时间排序
- 要给人读的本地化写法用 `formatLocalDate()`（`2025年1月15日` / `Jan 15, 2025`）
- 相对时间走词典（`3 天前` / `3 days ago`），数字走 `Intl.NumberFormat`

### 19.8 语言的确定顺序

1. 用户在右上角手动选过 → 用他选的（`localStorage` 的 `duansheli:lang`）
2. 没选过 → 跟 `navigator.language` 走：`zh*` 给中文，其余给英文
3. 什么线索都没有 → 中文

**语言偏好不跟着备份走。** 这是刻意的：换设备、换人的时候，界面语言该跟着人走，
而不是跟着数据走。（对比：AI Key 也存在 localStorage，理由类似 —— 它属于这台设备。）

### 19.9 AI 提示词也翻了两份

提示词在 `src/ai/promptText/`，中英各一份，按当前语言取。英文版是镜像不是重写：
规则编号、JSON 字段名、段落顺序都保持一致，方便对照维护。

英文版**多了一条规则**，这条很重要：

> …never translate the user's own data. Category names, location names, tag names and
> attribute names must be reproduced **exactly as they appear in the draft or in the
> existing lists** — even when they are in Chinese.

不加它，模型会「礼貌地」把你数据里的「衣物」输出成 `Clothing`，
于是凭空多出一个分类，你的数据被劈成两半。

一个已知的小代价：切语言会让 system 消息的前缀变化一次，
DeepSeek 的前缀缓存那一轮失效。可以接受 —— 没人会一轮一轮地切语言。

### 19.10 怎么防止以后再漏翻

漏翻有个坏特性：**编译过、测试也过**（测试环境锁中文），只有切到英文才看得出来。
所以单独写了一个审计脚本：

```bash
npm run audit:i18n
```

它做两件事：

1. **扫 `src/` 下所有界面文件**，去掉注释后找中文。任何一处写死的中文都会报出来。
   允许保留的例外是**显式白名单**（词典本身、中文提示词、
   `parse.ts` 里容错用的中文键名别名、`expiry.ts` 认中文日期的正则），每条都带理由。
2. **把两份词典拍平对一遍**：key 集合、插值占位符、单复数配对。
   `tsc` 挡住的是「少了 key」，这里补上「key 都在但 `{count}` 在一边漏了」那一类。

当前状态：界面文件里**零处写死的中文**，两份词典各 1141 条、key 与占位符完全对齐，
并且**文案里不许出现 markdown 星号**（`audit-i18n.mjs` 单独查这一条）。

## 20. 活动合集（旅行 / 学习 / 搬家）

### 20.1 它回答的是什么问题

数据模型里本来有两个维度：**位置**回答「东西在哪儿」，**分类**回答「它是什么」。
但用起来很快会撞上第三个问题：

> 明天出发，我该带的东西都齐了吗？

这个问题既不是位置也不是分类 —— 旅行要带的东西散落在衣柜、书桌、床头柜里，
分类上也五花八门（电子、日用品、药品）。所以需要第三个维度：
**「为了做这件事，得凑齐哪些东西」**。

### 20.2 为什么单独立一个实体，而不是拿标签凑合

标签已经在回答「什么情境」了（想送人、舍不得扔），看起来也能塞下「旅行」。
但两者的**性质**不一样：

| | 标签 | 活动 |
|---|---|---|
| 回答 | 这件东西对我意味着什么 | 为了这件事要凑齐什么 |
| 形状 | 一个轻量标记，挂几个都自然 | 一份可以浏览、可以核对的清单 |
| 数量 | 会越攒越多 | 通常就那么几个 |

混在一起的直接坏处：拿标签当活动的话，「旅行」会和「想送人」并排出现在
标签筛选里 —— 两个完全不同性质的维度被压成一层，越用越乱。

所以活动是**独立实体**，有自己的一页、自己的名字和备注。

### 20.3 数据形状

```ts
interface Collection {
  id: string
  name: string
  note: string      // 自由备注，如「三天两夜，爬山」
  order: number
  createdAt: string
}

interface Item {
  // ...
  collectionIds: string[]   // 多对多，和 categoryIds 同一个形状
}
```

两个刻意的决定：

**一、用 id 而不是名字。** 标签是用名字当 key 的（`Item.tags: string[]`），
代价是改名要全表扫一遍把旧名字换掉（`renameTag` 就是这么写的）。
活动会被改名，而且活动比标签更"重"，所以直接用 id —— 改名就只是改一个字段。

**二、多对多。** 充电宝既在「旅行」也在「出差」很正常，
和「一件东西可以同时属于多个分类」是同一个形状，代码也共用同一套写法。

### 20.4 一条硬规矩：删活动绝不删物品

这是整个功能里**唯一一个真正危险的操作**，所以规则写死：

> 删掉一个活动，只解除关联。里面的物品**一件都不会少**。

理由很直白：你为了旅行准备的那些东西，不会因为旅行结束了就该被删掉。
将来还要用，只是不再属于这个活动了。

实现上就是 `deleteCollection` 只做两件事：把活动从 `collections` 里去掉，
把每件相关物品的 `collectionIds` 里那一项去掉。**不碰 `status`、不碰别的字段。**

界面上配套做了三件事：

- 确认框里明确写「删掉的是这个活动本身，里面的物品一个都不会删」
- 删完的提示带上实际影响的件数（`已删除「旅行」，3 件物品留在原处`）
- 有专门的测试守着：删前删后 `data.items.length` 必须相等

### 20.5 首次启动不预置任何活动

分类和位置能预置，是因为「家里有哪些房间、东西分几类」几乎共通。
活动完全因人而异 —— 给不旅行的人塞一个「旅行」只是噪音，
而且**空的合集比没有更让人困惑**（「这个旅行是干嘛的？」）。

所以种子数据里 `collections: []`，由页面上的空状态去解释它能干什么。
（`示例数据-导入用.json` 里给了「旅行 / 学习 / 搬家」三个 —— 那是演示数据，
该把用法直接摆出来。）

### 20.6 和 AI 的关系（暂时不做）

AI 现在**不认识活动**。这一版刻意没做，原因是：
让模型自己往活动里塞东西，很容易凑出一堆似是而非的清单，而「要不要带这个」
恰恰是用户自己最清楚、最不该外包的判断。

不过数据层已经留好了口子：`DraftApplyItem.collectionIds` 是可选的，
而且**更新已有物品时不传就等于「保持原样」而不是清空** ——
否则每次让 AI 改个名字，都会把物品身上的活动全抹掉。

### 20.7 数据版本

`SCHEMA_VERSION` 3 → 4。老备份（v3）导入时 `collections` 读成空数组，
`Item.collectionIds` 补成空数组，不需要额外的迁移逻辑。
指向不存在活动的引用会被清掉并如实提示 —— 留一个悬空 id 比清掉更糟，
它会让界面上出现一个点进去什么都没有的活动。

## 21. 清单（一次性的待办）

### 21.1 为什么在「活动」之外还要再来一个东西

第 20 章的活动合集是**模板**：旅行要带的东西攒一次，以后每次出门都能用。
但真正出门前一晚要面对的是另一个问题：

> 这一次真带了哪些？还有几件没装包？

模板回答不了这个 —— 你要的是一个**能打钩、办完就能扔**的东西。
所以清单是独立的一层：**活动 = 模板（长期），清单 = 这次的实例（临时）**。

| | 活动合集 | 清单 |
|---|---|---|
| 存的是 | 应该带什么 | 这次要带什么、办了没 |
| 能打钩吗 | 不能 | 能 |
| 删了心疼吗 | 会 | 不会，本来就是临时的 |
| 会一直留着吗 | 会 | 用完就删 |

**为什么不是给活动加一个「已备齐」的勾**（第一版我确实是这么想的）：
那份勾会长期留在活动上，于是下次旅行时你看到的会是**上次**的打钩状态，
还得手动全部清掉重来。把「这次的」和「长期的」分成两个东西，
就不存在「该不该清」这个问题了。

### 21.2 两种建法

1. **从活动**：进活动 → 勾选这次要带的那几件 → 「生成清单」
2. **从物品**：在物品列表里勾选几件 → 选中栏「新建清单」

两条路都走同一个 `createChecklist`，区别只是传不传 `fromCollectionId`。
从活动建的时候取的是**勾选的子集**而不是「全部」，正因为需求是
「手动在活动那里勾选变成清单」。

### 21.3 条目是快照，不是引用

```ts
interface ChecklistEntry {
  id: string
  itemId: string | null   // 库里没有的东西就是 null
  name: string            // ← 抄下来的，不是引用
  quantity: number        // ← 也是抄下来的
  checked: boolean
}
```

三个理由都是实际会遇到的：

1. **物品改名了，清单该保持原样。** 清单记的是「当时决定要带什么」，
   不是「这件东西现在叫什么」。
2. **物品被删了，清单不该变成一行空白。** 界面上标一个「已不在库里」就够了。
3. **清单里会有库里根本没有的东西**（「顺路买瓶水」），那些条目没有 itemId 可查。

所以 `itemId` 只是个**可能失效的链接**，取用前一定判存在。

### 21.4 清单里的编辑不写回库

在清单里改名字、改数量，**只改清单上的这一条**，不动库里的物品。
「充电宝」在清单里写成「充电宝（借的）」，不该把物品也改了名 ——
那是「这次带的东西」的叫法，不是那件东西的名字。

有测试守着：改完清单条目之后断言物品的 `name` / `quantity` 一个字节都没变。

### 21.5 合并导入时的保守策略

清单按 id 去重，**id 撞了就整份保留本地那份**，不做字段级合并。

因为清单里有「打没打钩」这种状态。两边各勾了一部分的话，
无论怎么合并都会丢掉另一半的打钩信息，而用户看到的会是
「我明明勾好了，怎么又变回没勾」—— 那比「保留了旧的那份」更难解释。

### 21.6 校验：坏一条只跳那一条

别的实体坏一条就整条丢掉，清单不一样：

> 一条条目缺字段就跳过那一条，**剩下的照留**。

因为清单是用户临时攒的。为了第 3 条格式不对就把整份 20 条都扔掉，
比丢一条糟得多。条目 id 缺失时也**补一个**而不是丢掉 —— 它还有用。

### 21.7 数据版本

`SCHEMA_VERSION` 4 → 5。老备份（v4）导入时 `checklists` 读成空数组，
不需要额外的迁移逻辑。

## 22. 数据体检（"我的数据不见了"）

### 22.1 问题：三种真相，一个样子

数据是按**网址**隔离的（第 3 章）。于是「我的数据没了」这句话背后
其实是三种完全不同的情况，而它们在界面上**长得一模一样 —— 都是一张空列表**：

| 真相 | 该做什么 |
|---|---|
| 数据在，只是你现在站在**另一个网址**下 | 去那个地址打开 |
| 主记录真没了，但**快照还在** | 回退，东西能救回来 |
| 这个网址下本来就没存过东西 | 不用找了 |

只给一个空列表，用户只能自己猜。而人在这种时候的默认结论是
「数据没了」，然后放弃 —— 恰恰在**第二行**那种情况里，
数据完好无损地躺在快照里，一按就回来了。

所以 `src/storage/diagnose.ts` 把当前网址下的**原始事实**读出来：
库在不在、主记录有多少件物品、快照几份、最早和最新分别是什么时候。

### 22.2 结论只有四种，而且必须互斥

```ts
type DiagnosisVerdict = 'ok' | 'restorable' | 'empty' | 'unreadable'
```

判定顺序是有讲究的：

```ts
if (unreadable)                                          → 'unreadable'
else if (app.exists && (app.itemCount > 0 || maxItems === 0)) → 'ok'
else if (snapshots.count > 0 && maxItems > app.itemCount)     → 'restorable'
else                                                     → 'empty'
```

三条容易搞错的地方：

1. **「读不出来」必须排在第一位。** 读失败时 `snapshots.count` 也是 0，
   如果不先判它，就会得出「没有快照」—— 体检自己变成第二个骗人的地方。
   实测这条最要紧：用户正在找数据的时候，最不能接受的答案就是
   「你没有备份」，而真相是「没读到备份」。

2. **只有「当前一件都没有」才喊「可恢复」。** 删掉几件物品是正常操作，
   快照本来就会比当前状态多。若只要 `快照 > 当前` 就报警，
   用户每删一件东西都被吓一次，警报多了就没人信了 —— 那才真危险。

3. **`maxItems > itemCount` 不能省。** 「有没有快照」和「快照里有没有东西」
   是两件事：清空数据之后随手产生的快照物品数是 0，回退过去什么也拿不回来。
   只看 `count` 就报「可恢复」，等于让用户白折腾一趟。
   （这一条是**变异测试**逼出来的：把条件删掉后最初没有任何用例变红，
   说明用例漏了这个分支，补上之后条件就成了有守着的。）

还有一个容易自相矛盾的地方：`verdict === 'empty'` 但快照列表里明明列着 2 份。
所以界面按 `snapshots.count` 分两句说 —— 一句「也没有快照」，
一句「现有那些快照里也是空的」。**自相矛盾的界面比不说话的界面更糟。**

### 22.3 只读，而且不碰不该碰的东西

两条硬性边界，都有测试守着：

- **体检不写任何东西。** 写的话，「打开设置随便看看」就会产生快照、
  顶掉真正有价值的旧快照。用例跑三次体检，然后断言快照份数没变。
- **只列 localStorage 的键名，绝不读值。** 那些值里躺着 API Key
  （第 16 章）。用例断言体检结果的序列化文本里搜不到 Key 的内容 ——
  这条要是破了，等于把密钥印在屏幕上。

### 22.4 自动跑，不指望用户发现按钮

打开设置页时自动体检一次。会点进设置页找数据的人往往已经慌了，
不该再要求他自己看出「要点哪个按钮」。体检是只读的，所以自动跑没有代价。

同一页的「自动快照」区块原本把读取失败**静默吞掉**（`catch {}`），
列表空着看起来就是「一份备份都没有」。这跟上面的道理一样：
**失败必须说出来**，否则它会伪装成最坏的那个结论。现在失败时
那一格显示错误信息，而不是「还没有任何快照」。

### 22.5 顺手修掉的一个渲染 bug

`t()` 只做 `{变量}` 插值，**不认任何 markdown**。
第 19 章加的「数据按网址隔离」那句文案里写了 `**网址**`，
界面上就会原样显示两个星号。

这类错误最阴的地方在于它**能通过所有既有门禁**：
中英两边写一样的星号时，词典 key 对得齐、插值占位符也对得齐，
`tsc` 和测试全都绿的（测试环境锁中文，而中文那份也带着星号）。

处理方式两条：

1. 文案拆成 `storageOriginHintBefore` / `...Strong` / `...After` 三段，
   在 JSX 里把中段包 `<strong>`。这也是这个项目里 `xxxStrong`/`xxxBold`
   那套命名一直以来的用法。
2. `scripts/audit-i18n.mjs` 加一条检查：**词典值里不许出现 `**`**。
   用变异验证过 —— 往任意一条文案里塞回星号，审计立刻以非 0 退出。

### 22.6 测试怎么注入「读失败」

「读不出来」这条分支在生产上没法按需触发，所以
`diagnoseLocalData(source?)` 收一个可选的读取源：

```ts
export interface DiagnosisSource {
  getApp: () => Promise<AppData | undefined>
  getSnapshots: () => Promise<Snapshot[]>
  dbExists: () => Promise<boolean | null>
  estimate: () => Promise<{ usage: number; quota: number } | null>
}
```

默认值就是真实实现（真实 IndexedDB），传一份会抛错的进去就能测错误分支。
这是这个项目里**唯一**为了可测性留的注入点 —— 其余测试全部走真实链路。
理由：错误分支是「一旦出错就骗人」的那一类，不能只靠读代码确认。

## 23. AI 会话状态：跨页面活着，但不落盘

### 23.1 原来错在哪

`Ai.tsx` 把对话、历史、草稿全放在组件自己的 `useState` 里。
于是**去别的页面转一圈再回来，这些全归零**：

- 聊到一半的对话没了
- AI 已经提取好、还**没采纳**的草稿也没了
- 只能重新让 AI 整理一遍 —— 白烧一整轮 token，而这正是用户最在意的东西

用户是这么报的：「我发现现在我一切换，我跟 ai 的对话就没了」。

顺带澄清两个容易搞混的：

- **切中英文不会丢。** 路由上没有 `key={lang}`，`setLang` 只是让组件
  重新渲染（`useSyncExternalStore`），并不会卸载它们。
- **这不是回归。** `git log -S 'ai-chat'` 显示从 `781b103` 起就没持久化过，
  一直是组件内状态；只是平时不容易注意到。

### 23.2 设计：内存级 store，而且**刻意不落盘**

新增 `src/store/useAiSessionStore.ts`，把这些搬进去：
`bubbles` / `history` / `drafts` / `changedKeys` / `removedKeys` /
`error` / `running` / `usage` / `lastTurnUsage`。

**不落盘是用户的明确选择**（「只在页面之间活着，刷新就清空」），
而且和省 token 是同一件事：历史会一轮轮累积进 prompt，
存下来就意味着下次打开还在为它付费。「新对话」按钮才是真正的重置开关。

有一条用例专门盯着这条边界：往会话里塞一个标记字符串，然后断言它在
localStorage、IndexedDB 的 `kv` 表和主数据记录里**都搜不到**。
不写这条的话，「顺手存一下吧，用户肯定会高兴」是个太容易做的改动。

### 23.3 随之而来的一个真问题：草稿是「针对某一份数据」的计划

会话活得比页面久，就冒出一个以前不存在的问题。

**草稿不是一份独立的东西。** 每一条的 `sourceItemId` / `locationId` /
`matchedCategoryIds` 都是**当时那份数据**里的 id。如果这中间数据被
**整体替换**过（清空 / 导入覆盖 / 回退快照 / 恢复脚手架），那些 id 就
指不到任何东西了。

后果不是「会建错东西」，而是更隐蔽的一种：
`draftsToApply` 对「有 `sourceItemId` 但物品找不到」的处理是
**静默 `continue`**（`src/ai/convert.ts`），于是用户点「采纳」会得到一个
**悄悄少了几条**的结果，界面上还不会说哪一条为什么不见了。

> 这一条我一开始判断错了：我以为会「把清掉的物品当新物品建回来」。
> 那是对 `applyDraftItems` 行为的推断（它确实会在 `existingId` 找不到时
> 走创建分支），但沿着 UI 的真实路径推下去，`draftsToApply` 早就把它
> 过滤掉了，根本到不了那一步。**错的理由不能用**，所以改成了上面这个
> 能复现、也写了用例钉住的说法（见 `tests/aiSession.ts` 里那条
> 「数据换掉之后，它的一部分会被静默丢掉」）。

所以 `useAppStore` 里多了一个 `invalidateAiSession()`，挂在
**整体替换数据**的那几个操作上：`clearEverything` / `resetToSeed` /
`replaceAll` / `restoreFromSnapshot`。

两条分寸：

- **`mergeAll` 不挂。** 合并的语义是「把对方的并进来」，本地物品一件不少，
  草稿里的 id 依然指得到东西 —— 没有理由清掉用户的对话。
- **只在真的弄丢了东西的时候才提示。** 本来就没会话就不弹，
  否则「清空数据」会多出一条莫名其妙的提示。
- **绝不能挂到 `commit()` 上。** 那样每次改一件物品都会丢一次对话。
  有一条用例专门删一件物品然后断言会话完好，就是为了让那种改动立刻变红。

### 23.4 `ChatBubble` 挪了个位置

它原来定义在 `AiChatPanel.tsx` 里。会话状态搬到 store 之后，
store 就不该反过来去 import 一个**组件模块**的类型了 ——
挪到 `src/ai/chat.ts`（和 `ChatTurn` 作伴），它是领域类型，不是组件的一部分。

### 23.5 取消失效的问题也顺手修了

「取消」用的 `AbortController` 原本存在组件的 `useRef` 里，组件一卸载就没了 ——
于是「点了发送马上切走、回来再点取消」是无效的。现在放在模块级
（`setAiCancel` / `cancelAiRequest`）：它不需要触发重渲染
（按钮显隐由 `running` 决定），但**必须能跨组件卸载存活**。

另外 `send()` 开头加了 `running` 判断：状态跨页面存活之后，
「点了发送立刻切走、回来再点一次」本来可以发出两个并发请求。

## 24. 备用（多买的那些东西）

### 24.1 为什么不能复用「闲置」

两者都是「现在没在用」，但**意思正好相反**：

| | 闲置 | 备用 |
|---|---|---|
| 心态 | 留着也没用 | 特意留着的 |
| 页面框架 | 「闲置越久越说明它不该留在这里」 | 放两年也完全正常 |
| 主要动作 | 已处理（舍弃） | 取用 |

合成一个的话，闲置页会跑去劝你扔掉自己特意囤的东西；
而且「闲置占比」是断舍离的核心指标，把备用算进去会把这个数字弄脏。

所以 `ItemStatus` 加第三档 `spare`。状态机变成**两条支线**：

```
active(在用) ──标记闲置──> idle(闲置) ──舍弃──> discarded(已舍弃)
     ↕                                              ↑
  spare(备用) ──────────────────舍弃────────────────┘
```

`SCHEMA_VERSION` 5 → 6。这一档加的是**校验规则**：
老程序读到 `status: 'spare'` 会认不出来，让它整份拒绝比让它
默默把那件物品的备用属性丢掉要好。

### 24.2 备用必须是**独立的记录**，不能是「同一个物品的第二个数字」

最直觉的设计是一条记录带两个数：`quantity`（在用）+ `spareCount`（备用）。
**但那样表达不了一件事：备用和在用的东西不在同一个地方。**

牙膏在卫生间、备用的两管在储物箱 —— 而 `Item` 只有**一个** `locationId`。
所以多买的那几件必须是独立记录，才能各自有位置。
（这也是用户自己的习惯：「我一般就把备用的统一放在一个盒子里」。）

推论：「拆出备用」出来的那条是**同款的一个副本** ——
名字、分类、标签、属性、备注、有效期、所属活动全部照抄，
只有 id / 数量 / 状态 / 位置不同。备注也照抄是有意的：虽然备注有时是
「还剩半瓶」这种和单件绑定的说法，但「拆出来的和原来那条一样」这条规则
更好预测，而且抄错了看得见、改得掉。

### 24.3 取用：两种分支，同一件事

用户明确选的是「取完把这件就变成在用」。实现上把它做**严格一致**：

| 备用记录 | 取用一件之后 |
|---|---|
| ×1 | 整条变成「在用」 |
| ×3 | 变成 ×2，剩下的继续待在备用区 |

两种情况都是「**刚好一件**从备用区出来、进入使用」，不会多也不会少。
所以 `takeSpareOne` 里那个 `if (quantity > 1)` 不是特例，
是同一条规则的两个结果。

**取用绝不进回收站。** 用户的直觉是对的 —— 回收站（「已舍弃」）是给
「真的扔了、但怕手滑」准备的；取用是**东西被用掉了**，两者不是一回事。
只有「舍弃」这个动作才会进回收站。

### 24.4 「拆出备用」的三个刻意的约束

1. **原处至少留 1 件。** 上限是「数量 − 1」。全拆走就不叫「拆出备用」了，
   那是「这一整条都变成备用」—— 是「标记备用」那个按钮干的事。
   两个动作走两条路，语义才不含糊。
2. **数量用 − / + 按钮，不用数字输入框。** 一是手机上更好按，
   二是这个项目在 jsdom 里**没法给输入框派事件**（见 tests/dom.ts），
   用按钮才能把这条路径真的测起来。
3. **位置会记住**（`UiPrefs.spareLocationId`）。备用基本收在同一个盒子里，
   每次重选纯属白费事。注意区分 `undefined`（用记住的那个）和
   `null`（我就是要未归位）—— 调用方要知道这个区别。

### 24.5 数量守恒是这一组测试的核心

备用功能说到底是在**挪件数**。这类算术一旦错，表现是
「东西总数悄悄变了」而不是报错，所以测试逐条钉死了：

- 拆分前后 `所有物品的 quantity 之和` 必须相等
- 取用一件之后必须**恰好**少 1
- 拆到上限时原处必须还剩 1

还有两条用**变异测试**验证过（删掉条件后必须有用例变红）：
`takeSpareOne` 里的 `quantity > 1`（决定「最后一件变在用」）、
`splitToSpare` 里的 `quantity - 1`（决定「原处留住 1 件」）。

### 24.6 界面上跟着改的几处

- **隐藏备用**：`UiPrefs.hideSpare` 默认开，和 `hideIdle` 是**两个独立开关** ——
  「闲置别碍事」和「备用别碍事」是两种不同的判断，合并成一个就没法只关其中一个。
  边界和 hideIdle 完全一致：只影响物品列表、主动筛选时不藏、必须有提示条。
- **录入表单的状态从「开关」改成「三选一」**。开关只能表达「是 / 不是」，
  而备用是第三条支线。顺带修了一个实打实的错：以前用开关时，
  **已舍弃的物品会被显示成「在用」**（因为 `checked={status === 'idle'}` 为假）。
  现在已舍弃单独说一句、指向回收站。
- **侧栏徽标显示件数不是条数**：囤东西的人关心的是「还剩 7 件」不是「还有 3 种」。
- **闲置占比的分母变大了**（备用算进「我的东西」）。这是如实记账：
  备用是你实实在在拥有的东西。副作用是备用越多那个比例显得越小 ——
  方向是**安全**的（提醒更温和，不会劝你处理特意囤的东西）。

## 25. 教会 AI 这个工具的词汇

### 25.1 用户报的那个 bug

> 「我在让 ai 助手修改的时候，我说闲置，他给我打了闲置标签，而不是放到闲置里面，
> 他好像还不知道我们的活动啊这些规则」

**根因不是模型笨，是输出格式里根本没有能装「闲置」的地方。**
`RawExtractedItem` 只有 name / quantity / categories / location / tags /
attributes / note / expiresAt —— 用户说「这个改成闲置」，模型唯一能塞的槽就是 `tags`。
它其实**听懂了**，只是没地方放。

同一件事的另一半：**活动根本不在提示词里**。模型不知道它存在，用户说「加进旅行」，
它无从下手，也不会说自己不知道。

所以修法必须是两层，缺一不可：

| 层 | 做什么 | 少了会怎样 |
|---|---|---|
| 结构 | 加 `status` 和 `collections` 两个字段 | 模型还是只能塞 tags |
| 词汇 | 明确告诉它这些词在本工具里的确切含义 | 模型一边填 status、一边照旧往 tags 里塞一份 |

### 25.2 概念表：一份，两个 system 都用

`promptText.conceptVocab` 是**独立一段**，被 `${}` 插进 `extractionSystem` 和
`chatSystem` 两处。为什么不各写一遍：它是同一份知识，而「改了一处忘了另一处」
会造出**录入时懂、对话时又不懂**的半截状态 —— 那正是这个 bug 的成因。

概念表里点名了工具里的**全部实体**，并对最容易混的两对做了明确切割：

- **备用 ⇄ 闲置**：一个是「特意留着的」，一个是「该处理的」。方向正好相反。
- **活动 ⇄ 清单**：一个是长期模板（旅行要带什么），一个是一次性待办（这次打包）。

还有一条是直接冲着这个 bug 去的：

> 用户说「标记为闲置 / 改成闲置」→ 用 status 字段，
> **绝对不要**把「闲置」「备用」这类词写进 tags。

> ⚠️ 提示词是模板字符串，**里面不能出现反引号** —— 会直接截断字符串。
> 我加规则时踩过一次（`status` 包了反引号），`tsc` 报的错是
> `TS1005: ',' expected`，位置指在规则行上，第一眼不容易联想到反引号。

### 25.3 「没提到状态」必须和「在用」分开

这是实现里最容易写错、而且**写错了会静默改坏数据**的一处。

直觉写法是「AI 没给状态 → 默认在用」。但那样会出这种事：

> 用户说「把旧手机的名字改成旧手机（淘汰）」。AI 只改了名字，
> 没提状态 → 草稿状态被填成「在用」→ 于是那件**闲置**的东西
> 被悄悄变回「在用」，闲置计时清零。

所以 `ItemDraft.status` 的类型是 `AiStatus | null`：

- `null` = AI **没提到** → 改已有物品时**保留原来的**（`mergeChatResponse` 里 `fresh.status ?? existing.status`）
- 新建时 `null` → 按「在用」

这个坑是**现成的用例抓出来的**：`tests/ai.ts` 里那条
「落库：带 existingId 的更新已有物品，不新建」断言了
「更新不该把它的闲置状态改掉」，我第一版直接把它弄红了。
老测试救了新功能 —— 保留它的价值就在这里。

### 25.4 指纹：只改状态也是一次改动

和当年有效期那个坑一模一样，而且更隐蔽：

> AI 把 `status` 从 idle 改成 spare，别的字段一个没动。
> 如果指纹里没有 status → 判定「没改动」→ 这一条被跳过 →
> **界面上什么都没发生**。用户只会觉得「AI 又没听懂」，
> 而实际上是程序把它的回答丢了。

所以 `status` 和 `collections` 都进了**两处**指纹：
`convert.ts` 的 `effectiveSignable` / `itemSignature`（决定要不要落库），
以及 `chat.ts` 的 `signature`（决定算不算「这一轮改动过」）。

**变异验证过**：把 `chat.ts` 里 `content.status ?? ''` 那一行删掉，
「只把闲置改成备用，必须被认成改动过」立刻变红。

### 25.5 活动只能复用，不能新建

和分类刻意不一样：

| | 分类 | 活动 |
|---|---|---|
| AI 能否提议新建 | 能（用户原文里的归类名是他自己的意图，界面上还有「采纳新分类」的勾选让他点头） | **不能** |
| 对不上怎么办 | 标成「新分类建议」，等用户勾选 | 记进 `droppedCollections`，界面上如实提示 |

理由是活动**没有那一层点头机制**。让模型随口造一个，用户会发现自己多出一堆
从没建过的活动 —— 那比它说「没有这个活动」糟得多。

### 25.6 AI 说「已舍弃」怎么办

`RawStatus` 里 `'discarded'` 是**单独一档**，不混在那三个合法状态里。
`mergeChatResponse` 把它转成一次 **removedIds 删除**：

- **不能忽略**：用户说「这个扔了吧」，界面上什么都不发生 —— 那看起来就是 AI 没听懂
- **不能直接写进 status**：那条路是「改字段」，而舍弃**要进回收站**（可恢复），
  两者走的机制不同

顺带一个收获：`DraftApplyItem.status` 的类型就是
`'active' | 'idle' | 'spare'`，所以**「status 被写成已舍弃」这件事在类型层面
就不可能**（测试里想断言这一点，TS 直接报 TS2367「两个类型没有重叠」）。
能用类型表达的保证，就不要用运行时断言。

### 25.7 顺带修掉的一个测试污染

写体检那组用例时，我造了一条 `at: 12345` 的畸形快照来验
「时间读不出来也不崩」，但**没清掉它**。后面 `aiSession` 那组会走到
`restoreFromSnapshot → pruneSnapshots → listSnapshots`，那里按 `at` 排序 ——
撞上这个数字就抛 `localeCompare is not a function`。

症状离病因极远（**体检测试把会话测试搞红了**），所以我把它记在这：
造畸形数据的用例必须自己收拾干净。

## 26. 落盘失败：连接被关掉时怎么办

### 26.1 用户报的错

> 「保存到本地失败：Failed to execute 'transaction' on 'IDBDatabase':
>   The database connection is closing.」

先把**不是原因**的东西排掉：

| 猜 | 查证 |
|---|---|
| 我们自己的版本升级把对方挤掉了 | `git log -S 'DB_VERSION = '` —— **从第一个提交起一直是 1**，不可能触发版本变更 |
| 代码里主动删了库 | `git grep deleteDatabase` —— 一次都没有 |
| IndexedDB 本身坏了 | 不是。这是**规范里明确定义**的行为，不是异常 |

真正的原因是：**IndexedDB 的连接不是我们能独占的东西**。下面这些都会把它从底下关掉，
而且**都不是 bug**，是浏览器的正常行为：

- 另一个标签页要升级数据库版本（会先触发 `versionchange`）
- 浏览器在回收存储空间
- 用户在开发者工具里点了「清除站点数据」
- 页面在后台被挂起太久

### 26.2 代码原来的问题：死连接会用到底

```ts
let dbPromise: Promise<IDBDatabase> | null = null   // 缓存住，图省事

db.onversionchange = () => {
  db.close()
  dbPromise = null      // ← 只把缓存丢了，就这些
}
```

两个洞：

1. **正在飞的那次操作**已经从这个 promise 拿到了 `db`，接着 `db.transaction()` ——
   而连接正在关闭，于是抛 `InvalidStateError`。这正是用户看到的那句。
2. 更糟的是 `onclose` **根本没处理**。连接被单方面关掉时，
   缓存里那个 `db` 还是死的，要**一直抛到页面刷新为止** ——
   那期间用户每一次改动都存不进去，而他只会看到一句他看不懂的报错。

### 26.3 修法：认出「连接没了」，重开一个再试一次

`withFreshRetry` 包住全部读写：

```ts
async function withFreshRetry<T>(attempt: () => Promise<T>): Promise<T> {
  const tokenBefore = dbToken
  try {
    return await attempt()
  } catch (err) {
    const connectionGone = isConnectionLost(err) || dbToken !== tokenBefore
    if (!connectionGone) throw err
    forgetDb()          // 丢掉死连接
    return attempt()    // 重开一个再试，只试这一次
  }
}
```

三个值得说的细节：

1. **不能只看错误名。** `InvalidStateError` 覆盖了 `db.transaction()` 那一句，
   但「写到一半连接被关」时事务是 **abort**，抛出来的错误名不是它，光看名字会漏。
   所以再加一条 `dbToken` 判断：这次操作**进行期间**连接被废掉过，也算。
2. **重试是安全的，因为这个模块上的写操作全都是幂等的**：
   整条记录 put、按 id put 快照、按键 delete、clear。重试一遍最多是再写一次，
   所以「第一次其实成功了、只是连接在完成前挂了」也不会写坏。
3. **只试两次。** 第二次还失败就如实抛出去 —— 那时候多半是真出问题了。

`onclose` 也补上了（部分浏览器支持），它只是一层保险，真正的兜底是重试。

### 26.4 光修好还不够：失败了必须让人知道

落盘失败是最危险的**静默失败**：`commit` 是**先同步更新界面**（保证手感跟手）、
再异步落盘的。所以写失败时界面已经按新数据渲染好了，**看起来一切正常**，
但刷新就没了。

原来只有一条会自己消失的 toast，三秒后用户就以为没事了。所以加了
**一个挂在壳上的持久横幅**（`AppShell`，所以每一页都看得到）：

```
⚠️ 这次改动没能存进本地：<真实原因>。……
   你现在看到的内容还在内存里，但一刷新就会丢 —— 请点「重试保存」。
                                    [重试保存]  [先导出备份]
```

**「先导出备份」是刻意放在那儿的最重要一个按钮**：如果浏览器就是不给写本地，
那份还在内存里的数据至少能导成文件带走。这是通往「数据不丢」的最后一条路，
不该让用户自己去设置页找。

### 26.5 这一组测试是怎么写的

不是打桩，而是**真的把连接关掉**：

```ts
const db = await openDb()   // 先让连接建立并被缓存
await idbGet(STORE_APP, APP_DATA_KEY)
db.close()                  // ← 模拟「另一个标签页 / 浏览器 / 开发者工具」把它关了
await idbPut(STORE_APP, data, APP_DATA_KEY)   // 旧代码在这里炸
```

**变异验证过**：把重试关掉，这一组 8 条全红，报的就是用户那句
`InvalidStateError`。

> ⚠️ 那次变异还顺带弄红了**另外 26 条**无关用例（体检、会话、导出……）。
> 原因很直白：连接是全局共享的，被关掉之后如果没有重试，
> 后面每一个碰存储的用例都会失败。**以后看到一大片无关用例同时红，
> 先怀疑存储层。** 这条已经写进 `tests/storage.ts` 的文件头。

## 27. 白屏与死转圈：把「什么都没有」变成「写清楚了的一段话」

### 27.1 起因

用户报「`/#/items` 打不开了」，而我能查的全是好的：
Vite 编译每个模块都 200、开发期没有 Service Worker、
415 条测试全绿（包括用老数据走完整 `init()` 再渲染每条路由）。

**白屏是最糟的失败形态**：用户不知道该干什么，我也拿不到任何信息 ——
只能来回猜。所以这一轮修的不是某个具体 bug，而是**让失败自己说话**。

### 27.2 两个死胡同

| 现象 | 成因 | 原来会怎样 |
|---|---|---|
| **白屏** | React 18 里渲染期未捕获的异常会让它**卸载整棵树** | 一片空白，屏幕上没有任何线索 |
| **白屏** | 更早的失败：模块**求值期间**就抛（顶层常量算错、import 了不存在的东西） | 连 React 都没开始跑，同样空白 |
| **一直转圈** | `init()` 的 promise 永远不 settle | 没有超时、没有说明、没有重试，只能干看着 |

### 27.3 三层兜底，各管一段

```
bootGuard（纯 DOM，模块求值时就装上）
   ↓ 管不到就交给
ErrorBoundary（React 已经跑起来了，能画出像样的界面）
   ↓ 再往下
init 超时提示（界面是好的，只是数据打不开）
```

**为什么 bootGuard 要用纯 DOM、而且文案写死成中英双语**：
它要在「应用已经挂掉」的时候还能画出来，而挂掉的很可能正是 i18n 或 React
本身 —— 所以它不能 import 它们，也不能等 CSS。这是全项目**唯一**一处
故意不做国际化的地方，理由就是「做了就可能失效」，
`scripts/audit-i18n.mjs` 里为它开了白名单。

### 27.4 一个很容易写错、写错了就白干的地方

**ES 模块的求值顺序是：先把所有 import 求值完，再跑本模块的正文。**

所以如果兜底只在 `main.tsx` 的正文里被调用：

```ts
import { App } from './App'                        // ← 这条链先求值
import { installBootGuard } from './lib/bootGuard'
installBootGuard()                                 // ← 轮不到执行
```

那么当 `./App` 那条依赖链在求值期间就抛错时，`main.tsx` 的正文根本不会跑，
兜底**没装上** —— 而「模块加载期就抛」恰恰是白屏最常见的成因。

所以 `installBootGuard()` 写在 `bootGuard.ts` 的**模块作用域**里自己执行，
`main.tsx` 只把它作为**第一条 import**（模块副作用导入）。
有一条用例专门守这个：**故意不调用它**，直接派发一个 error 事件，
装上了才画得出面板。变异验证过 —— 把那句自己调用注释掉，这条立刻红。

### 27.5 原始错误要原样贴出来

ErrorBoundary 的兜底屏上有一段 `.crash-detail`，把 `error.name: message`
原样显示。难看，但那是用户唯一能复制给我、而我唯一能据以定位的东西。

> 顺带一个小例子：`console.error` 那句我一开始写成中文，
> `audit:i18n` 立刻报「界面文件里有写死的中文」。它不是界面文案、
> 是给开发者看的，所以改成英文，并在原地注明了「这不是漏翻，别翻回去」。

## 28. 真凶：`undefined !== null` 是 true

### 28.1 兜底屏直接把答案说出来了

装上兜底之后，用户拿到的是一行原文：

```
TypeError: Cannot read properties of undefined (reading 'message')
```

而这一行指向的位置是 **我自己刚写的代码**：

```tsx
const saveFailure = useAppStore((s) => s.saveFailure)
...
{saveFailure !== null ? ... saveFailure.message ...}
```

**`undefined !== null` 是 `true`。**
所以只要 `saveFailure` 是 `undefined`，这个判断放行，下一行读 `.message`
就抛错 —— ErrorBoundary 兜住之前，那就是一整片白屏。

### 28.2 为什么测试没抓到

所有用例都只给了两种取值：一个真的对象，或者显式的 `null`。
**`undefined` 那一档没人试过** —— 而它恰恰是「状态里少了个键」的默认样子。

要捏出这个状态很便宜，所以现在钉成了用例：

```ts
useAppStore.setState({ saveFailure: undefined as unknown as null })
// 渲染每一条路由，一条都不许崩
```

**变异验证过**：把那句 `?? null` 删掉，这条用例立刻红，
报的就是用户看到的那串原文。

### 28.3 这类「少了个键」的状态是怎么来的

最现实的一条路是**开发时的热更新**：Vite 换了新模块，但 store 实例可能还是旧的
（新加的字段在老实例上根本不存在）。用户那个开发服务器和浏览器标签页
跨了十几个提交一直在热更新，正好是这个场景。

> 这也解释了它为什么「硬刷新也不好」：期间模块图是**混合**的 ——
> 新组件的代码 + 旧 store 的实例。真正的解法是重启开发服务器。

### 28.4 为什么这种写法特别危险

**`!== null` 看起来像是在安全检查，其实不是。**
它只挡住了 `null` 一种空值，放过了 `undefined`；而后面跟的是**读属性**，
于是就变成了一次崩溃。区分两种空值只在「语义上要区分」时才有意义 ——
这里并不需要，它只是想问「有没有值」。

所以修法是**在数据进来的地方归一化**，而不是在每个使用点补判断：

```tsx
const saveFailure = useAppStore((s) => s.saveFailure ?? null)
```

顺手把同一个模式在别处也扫了一遍。结论是**只有这一处会崩**，
因为只有它是「读对象属性」；其余几处分别是渲染字符串、数字、或者
`statusLabel()`（它有 `default` 分支兜着，传 undefined 也安全）。
另外两处还是收紧了：

- **ErrorBoundary 自己**改成 `error == null` —— 这个屏幕**自己绝对不能崩**，
  它崩了就还是一整片白屏，正是它存在的意义所在
- 草稿预览的状态徽章改成 `draft.status != null`

## 29. 从 CSV 清单恢复（只能救回一部分）

### 29.1 起因

用户问「我这个 CSV 为什么不能导入」。查下来是**两道门**：

1. 文件选择器写的是 `accept=".json,application/json"` —— **`.csv` 根本不显示**，
   连选都选不上
2. 就算硬塞进去，第一步 `JSON.parse` 就失败

而这是**设计如此**，`exportCsv.ts` 顶部写着理由：

> ⚠️ CSV 是**有损**格式：属性定义、分类顺序等结构信息不会保留，
> 因此它只能看、不能用来恢复数据。备份请用 JSON。

但那句设计的预设是「用户还有 JSON」。用户的情况是：
**那个地址的数据已经没了，CSV 是他唯一的备份。**
那时候「格式不完整」和「数据全没了」之间，前者显然好得多 ——
所以补上这条路，但**必须在界面上说清它补不回什么**。

### 29.2 设计：CSV → 一份标准 AppData → 复用现有导入流程

这是整个功能最要紧的一个决定。转换出来的是**标准 `AppData`**，
于是下面这些全部自动继承，一行都不用重写：

- 导入前的自动快照（`commit(..., 'import')`）
- 预览弹窗、覆盖/合并的选择
- 合并算法、悬空引用修复
- 导入报告

所以 `data/csvImport.ts` 是一个**纯函数**：进字符串、出一份数据 + 说明，
不碰 store、不碰 IndexedDB、不弹任何东西。副作用归零，因此特别好测。

### 29.3 补不回来的东西，以及为什么要把它写成用例

| 找不回来 | 原因 |
|---|---|
| 活动归属 | CSV 里没有这一列 |
| 清单 | 同上 |
| **分类的层级** | 导出时写的是**分类名字**（`categoryById.get(id)?.name`），父子关系丢了 |
| 属性类型 | 只有值，没有类型 / 选项；一律按文本建，单位从表头括号里取 |

`tests/csv.ts` 里有一条用例**专门验证这些损失真的存在**，
而不是只在文档和提示里写写：

> 构造一份带「衣物 › 上装」子分类、带活动、带清单的数据 →
> 导出成 CSV → 导回来 → 断言层级确实变平了、活动和清单确实是空的。

为什么值得这么写：界面上那句「活动 / 清单 / 分类层级找不回来」**必须是真的**。
哪天有人让 CSV 带上这些字段，这条用例会红 ——
提醒他同时把界面提示改掉，别让界面继续说假话。

### 29.4 一个读不出来的歧义：分类那一列

导出时 `categoryNames.join(' / ')` —— 把**多个分类名**用「 / 」拼起来。
而位置那一列是**完整路径**（`pathString`）。于是：

- 「位置」列：`家 / 卧室 / 衣柜` 是**路径**，能逐层还原成树 ✓
- 「分类」列：`衣物 / 日用品` 是**两条分类**，不是两层路径

两者看着一样，语义完全不同 —— 这是导出格式本身的歧义，改不掉了。
导入按「多条顶层分类」处理，并在提示里说明层级找不回来。

### 29.5 状态词表共用

CSV 的「状态」列写的是**导出当时的界面语言**（在用 / 闲置 / 备用 / 已舍弃，
英文界面导出来就是 In use / Idle / …），而 AI 那边也要认同一批词。

各写一份迟早会漂，而「认不出来」的表现是**状态悄悄没了**，不是报错。
所以词表搬到了中立的 `lib/statusWords.ts`，`ai/parse.ts` 和 `csvImport.ts` 共用。
（跟着一起进去的还有 `audit-i18n.mjs` 的白名单：那些中文是**要被解析的输入**，
不是要显示的文案 —— 翻译它反而认不出来了。）

### 29.6 拿真实文件核对过

补完解析器之后，用用户那份真实的 CSV 跑了一遍：

```
177 件全部解析，0 行跳过
40 个分类、0 个位置、5 个属性、1 个标签
状态分布：在用 172、闲置 5
```

顺带发现：那份清单里 **177 行的位置全是「未归位」** ——
也就是说他确实没给任何东西记位置，CSV 是忠实的，不是导出出了问题。

这个核对脚本留下来了，因为它跑的是**真实文件的形状**，
而单元测试用的是我造的例子：

```bash
node scripts/verify-csv-import.mjs "断舍离-物品清单-2026-10-04-1707.csv"
```

## 30. 拖拽：把物品拖到位置上、把备份拖进设置页

### 30.1 为什么最后还是做了拖拽

第 12 节记过一次取舍：M4 的**位置拖拽**放弃了，理由是 HTML5 拖放在触屏上不触发。
那条理由今天依然成立，但**拖什么**决定了这个代价划不划得来：

| | 拖位置 | 拖物品 |
|---|---|---|
| 操作频率 | 偶尔（建完树就很少动） | 高（一件东西换个地方放是日常） |
| 改错一个的代价 | 整棵子树跟着挪，还可能成环 | 一件东西回了错的地方，再拖一次就回得来 |
| 有没有替代路径 | 有（「移动到…」选择器） | 原本要「开详情 → 找位置 → 在选择器里翻到那一层」 |

`docs/README` 里那句「改归位不用点进详情页」就是这个动机：
右树就在旁边摆着，拖过去是最直接的说法，绕一大圈去填个表单完全不成比例。

所以结论不是「触屏不重要」，而是：**这个动作值得为触屏单独留一条替代路径。**
每条物品后面的「移到…」按钮走的和拖拽**同一段函数**（`handleDropItem`），
两边的行为不可能漂。以后要再加拖拽，先回答上面那张表。

### 30.2 实现上的三个决定

**（1）拖的是物品，认的是自定义 MIME。**
拖拽数据用 `application/x-duansheli-item`，不是 `text/plain`。
树的落点只认这个类型 —— 拖文字、拖文件从旁边经过时既不亮也不拦，
不会出现「随手拖个东西上来就把物品挪走了」。类型串由调用方传给 `TreeView`，
所以树本身对「拖的是什么」一无所知，分类树将来要用也能直接接。

**（2）「未归位」也是落点。**
落到它身上是**撤掉位置**，不是「没有动作」—— 代码里这两件事必须分开：
`onDrop(null, payload)` 和「不调用」是两码事。少了这条路径，东西拖出去就再也拖不回来。

**（3）拖回原地要说一声。**
`item.locationId === targetId` 时不写数据，但**要弹一句「本来就在这儿」**。
静默的成功和失效长得一模一样，用户只会以为拖拽没生效，然后反复拖。

### 30.3 一个必须写下来的注意点：高亮不能闪

行的 `dragleave` 在鼠标从行背景移到**行内的按钮**上时也会触发 ——
那时人还在这一行里。直接照着 `dragleave` 撤高亮，手一动高亮就闪。
所以判断用的是 `e.currentTarget.contains(e.relatedTarget)`：
还在这一行里就什么都不做。

高亮本身用**整圈描边**而不是只换底色：底色已经被「选中」占了，
而这两个状态可能同时出现（拖到自己当前所在的位置上就是这样），
只换底色的话那种情况完全看不出来。

### 30.4 导入：拖进来，而且整页都是落点

导入的落点挂在 **window** 上，不是只挂在那个虚线框上。两个理由：

1. 设置页很长，那个框不一定在视野里 —— 想拖的人不该先去找它；
2. 更要紧的是，**不接住这个事件，浏览器会把 `.json` 当成一个页面直接打开**，
   整个应用被顶掉。那比「没导入成功」难受得多，而这件事是躲不开的。

整页都是落点会不会误事？不会：拖进来的文件照样先过 `handleFile` 的校验，
再走「确认导入」那一步才可能写数据 —— 落错地方顶多多弹一个预览框，
而这个框取消掉不留任何痕迹。「选择文件」按钮保留着，是给键盘用户留的路。

虚线框和那句「拖进来就行」是这件事**唯一看得见的说法**：
不画出来，用户根本不会想到还能拖。所以框本身不处理事件，只负责亮。

### 30.5 实现细节：`dragover` 是每帧都在发的

拖拽经过时 `dragover` 会一直触发，直接 `setState` 会让整张设置页跟着每一帧重渲染。
所以用一个 ref 记住当前值，值没变就不进 `setState`。

同理，物品行上的 `draggable` **只在需要时写**：写 `draggable={false}`
是「明确声明这一行不可拖」，而这里想要的是「没这回事」。

## 31. 一次性数据整理：把分类层级改一下（以及为什么它长成这样）

### 31.1 事情本身

用户提的需求很朴素：「物品里面的衣服，全都加一个上级标题：衣服」。
现实是：他的顶层分类里散着「上衣 / 裤子 / 外套 / 鞋子 / 背心运动服 / 秋 / 睡衣 / 其他穿戴」，
想要的是一层「衣服」把它们收进去 —— **改的是分类的层级，不是物品**。

### 31.2 为什么这件事必须由他动手，而不是我

数据存在**浏览器**里（IndexedDB，而且按网址隔离），仓库里根本没有他的分类树。
所以任何「我来改」的说法都是假的，能做的是：把改动算好、把风险兜住、
把他的手势压到最少。

于是有了两个入口，共用同一份**纯逻辑**：

| 入口 | 什么时候用 | 他要做什么 |
|---|---|---|
| `fix-categories.html` | 数据就在这个网址下（本地开发服务器） | 打开链接 → 看一眼 → 点一下 |
| `scripts/fix-category-parent.mjs` | 数据在别的网址下（比如 GitHub Pages） | 导出 JSON → 我改 → 他导入 |

### 31.3 最要紧的一条设计：算和写分开

`scripts/category-parent-fix.ts` 是**纯函数**：输入旧的 `categories`/`items`，
输出新的 `categories` 加一份「改了什么」的报告。两个入口都只是搬数据。

这么拆的理由很直接：**这个改动没法用眼睛验**。改完只是树的样子变了，
看不出对错，而分类层级是用户一层层攒出来的，弄乱了很难复原。所以：
算的部分全部由用例钉死（`tests/categoryFix.ts`，12 条），
写的那一头只负责「读 → 存快照 → 写 → 再读回来核对」。

### 31.4 用例真的抓到了两个 bug

这一组用例不是走形式 —— 写完第一版跑起来，红了两处，而且都是会**静默毁数据**的那种：

1. **新建的上级分类没进数组**。代码算了它的顺序（`topOrder`），却只在「顺序表」里
   放了它，忘了把它塞回 `categories`。结果是所有被挪的分类挂在一个**不存在的父级**上 ——
   界面上的表现是它们从分类树里消失（找不到父节点），而数据看起来「没报错」。
2. **第二次执行会改变顶层的顺序**。幂等性没写全：没有东西可挪时，
   插入位置退化成了「末尾」，于是「衣服」从第 2 位跑到最后一位。
   用户手抖点两次、或者不放心再跑一次，层级就会莫名其妙地变一次。

第 2 条尤其说明问题：**幂等不是「顺手加的一条断言」，而是这类操作的必答题**。
凡是「重排顺序」的工具，都要问一句「再跑一次会怎样」。

### 31.5 三条刻意的保守

- **同名但不在顶层 → 停下来**，不猜。复用会把「衣服」从它原来的位置拔走，
  新建又会造出两个「衣服」，两种选择都可能是错的，只有用户知道他要哪个。
- **写之前先存快照**（`reason: 'manual'`），而且工具页上还额外给了一个
  「撤销刚才那次改动」—— 两条退路，一条走应用的「设置 → 快照回退」，一条就在眼皮底下。
- **幂等**：重复执行必须一个字节都不改（见 31.4 第 2 条）。

### 32.1 最严重的一条：`init()` 会把刚录的东西冲掉（#10）

用户的原话是「我发现他有时候莫名其妙会把我数据给弄丢，我不知道为什么，
就我刚刚才新建的东西，过了一会他就不见了」。

**这是个真的竞态，而且能一行代码复现。** 落盘是异步的、排队的（`writeChain`），
于是有一个窗口：

1. 用户新建了一件东西 → `commit()` 立刻改内存、把写盘排进队列
2. 这一步还没轮到（IndexedDB 是异步的）
3. `init()` 被再调用一次（组件重新挂载 / 用户点了「重试」）
4. `init` 从盘上读回来的是**没有那件东西的旧数据**，然后 set 进 store
5. 刚录的东西在眼前消失，而且**没有任何提示**

第 5 步是最糟的：数据其实还在盘上（写入队列最后还是会成功），但界面上已经没了；
如果用户接着又录了别的东西，那次 commit 会以**丢掉那件东西的内存快照**为基准
写盘 —— 东西就真的没了。

修法两条，都在 `init()` 里：

```ts
await writeChain                       // 先把排队中的写入等完，再读盘
if (dirtySinceFlush && saveFailure) {  // 上一次写盘失败时
  set({ status: 'ready' })             // 宁可不读，也不拿旧数据覆盖内存
  return
}
```

第二道是给「写盘失败」准备的：那时候盘上那份就是旧的，覆盖等于把
「界面上还看得见、还有机会导出或重试」的东西真的弄丢。

**变异验证过**：把 `await writeChain` 删掉，`tests/dataLoss.ts` 里两条
带 ★ 的用例立刻变红，报的正是用户描述的症状（`实际内存里的物品：（一件都没有）`）。

### 32.2 采纳不再等于清空（#1）

用户：「AI 采纳后聊天记录会消失，应该一直保留着，直到我自己手动选择新建。」

早期版本里采纳直接 `clearAiSession()`。改成一整套 `settleApplied()`，它做四件事：

1. 把这次真的落库的草稿从草稿区**移走**（它们已经是数据库里的事实了）
2. 清掉它们对应的 `removedKeys` —— 否则下一次采纳会把同一批物品**再进一次回收站**
3. 在聊天记录里补一条 `role: 'note'` 的说明 —— 「采纳了」是这段对话里发生过的事
4. **把落库后的真实 id 绑回那些没被采纳的草稿**（见下一条，这步是 #2 的一半）

对话气泡、历史、累计 token、以及**没被采纳的草稿**一律不动。
清空只由「新对话」按钮触发。

一个刻意的细节：那条说明走 `bubbles`，**不进 `history`**。history 是发给模型的
真实对话轮次，塞一条合成的 user 消息进去，模型会以为用户又说了那句话。
改成 `appliedSummary` 字段，在下一轮指令开头拼一句「上一批已经采纳落库了：棉签、碘伏棉签」
—— 否则用户接着说「刚才那批再改一下」，AI 手里已经没有那几条草稿了。

### 32.3 名字撞车：绝不替用户猜（#2 / #8）

用户的两句话合起来是一条规则：

> 「已有的东西更新位置或分类时，它有时候并不是更新，而会新建一个物品。
>   他必须要先核查我到底有没有，再来新建。除非我明确说了新建，他才不用调取，直接新建」
> 「在拉取已有的东西的时候，经常会识别不到我已有的东西……我告诉他我的仓库里有，但是他找不到」

分三层修，缺一层都不够：

**第一层：让它找得到。** `loadScope` 多了 `names`：

```
{ "names": ["棉签"] }   →  按名字子串匹配（忽略大小写和空白）
```

为什么这一条是关键：system 里只有「哪个分类有多少件」的统计，
而「棉签」可能在「日用」也可能在「药品」—— AI 猜不到该拉哪一支，只能说没找到。
用子串而不是精确匹配是刻意的：说「棉签」时「碘伏棉签」也该拉进来，
这正是用户期望的那件事。提示词里也写死了一条：**在没看到具体条目之前，绝对不要新建**。

**第二层：撞车了要问。** `findNameCollisions()` 找出「要新建、但名字和库里某件一样」
的草稿。这种条目**默认不进采纳计划**，界面上弹出确认：

```
棉签   库里已有这一条（位置：桌子 / 桌子下 / 蓝色柜 / 透明盒子）
       [就是它，改这一条]   [不是它，另建一条新的]
```

程序不给默认值：猜「新建」就是用户报的那个 bug；猜「更新」更糟 ——
动了他没让动的东西。可以逐条选，也可以全部选完再一次采纳。

**第三层：落库后把 id 绑回去。** 新建的草稿落库后才有 id，而草稿原来那个 key
是编出来的（`new-1`）。`ApplyDraftResult.appliedIds` 把「计划里第 i 条落到哪件物品」
报回来，`settleApplied` 再绑到草稿上。不绑的话：AI 新建了一盒棉签、用户采纳，
接着又说「把棉签数量改成 3」—— 那条草稿在 AI 那边仍然是「要新建的」，
于是库里多出第二盒。

> ⚠️ 这里有一处**下标陷阱**，我第一版就写错了：`draftsToApply` 会跳过
> 「没勾选」和「还在等确认」的条目，所以**草稿的下标**和**计划的下标**是两套东西。
> 混用的后果是「用户确认的是第二行，程序改了第一行」——界面上看起来完全正常。
> 现在 `DraftApplyResult.duplicates` 用的是计划下标，并且有一条用例专门构造
> 「第一条被跳过」的场景盯着它（`tests/ai.ts` 里那条带 ★ 的错位用例）。

### 32.4 快照的件数、回退的交代、两份快照的对比（#15 / #16）

**件数（#16）**：`listSnapshots()` 现在**以 `data.items.length` 为准**，
存的那个 `itemCount` 只当缓存（老快照或手工改过的备份可能对不上）。
理由很直接：这个数字是用户决定「回退到哪一份」时唯一的依据，
一个和内容对不上的数字会让他在最需要判断的那一刻判断错。
`createSnapshot()` 也是自己数一遍再写，不接受调用方传进来的数字。

**回退的交代**：回退**会**改变物品数量（那是它的作用），所以提示里把前后数字摆出来：

```
已回退：物品从 12 件变成 9 件（少了 3 件）。少掉的还在上一份快照里，可以再回退回来。
```

少了的时候用警示色 —— 那正是用户会慌的那一刻。

**对比（#15）**：设置页的快照行多了「对比」按钮（这份 ↔ 现在），
标题栏多了「对比两份快照」。`lib/diff.ts` 算出七类差别：

- **回退过去会少的那几件**（放最前面，这是最要紧的一块）
- 只在这一边多出来的 / 内容不一样的那几件
- 件数合计（**条数没变但东西多了**看得出来）
- 分类 / 位置 / 属性 / 标签 / 活动 / 清单的增删

它**只摆事实、不给建议**：哪一份是你要的，只有你自己知道，给错了建议比不给更糟。
两份完全一样时也明说「内容完全一致」，免得他为一个小数字白纠结。

### 32.5 合并：先把「会发生什么」摆出来（#14）

用户：「我发现合并反而会让总东西变少，这是一个bug。」

先查结论：**合并不减东西**。它就是「只做加法」—— 本地有、导入那份没有的一律留着
（唯一例外是修悬空引用，那不是删东西）。但报告里只有「新增/更新/未变」三个数字，
用户根本看不出来有没有东西被丢掉 —— 那三个数字少看一个，就成了「变少了」。

所以两件事：

1. **合并前先摆一份差异预览**（`mergeAppData` 是纯函数，先算一遍不写任何东西），
   点确认才真的合并。预览和「快照对比」复用同一个对话框 ——
   「合并会发生什么」和「两份快照差什么」本来就是同一个问题，
   写两套的结果通常是两边慢慢长歪。
2. **报告里明写「少了的东西：一件都没有」**，而且 `ImportReport.items.removed`
   **恒为 0**（写死的，不是算出来的），有测试断言这一条：
   「合并后物品总数 ≥ 合并前」在三条不同形状的数据上都跑一遍。

顺带把用户说的「哪些有冲突」做出来了：`nameConflicts` —— 名字一样、
但 id 不同的两条（本地一个「棉签」，导入文件里又有一个）。是不是同一件东西
只有用户知道（真有两根一样的棉签很正常），所以只并排摆出来，不替他判断。

### 32.6 只显示改动过的（#6）

用户第一次的说法：「当把他们拉进来未动的时候，不要把未动的也展示在预览的底下，
只展示修改的就行了。」

用户第二次的说法（说明第一版**没修到**）：

> 「现在我删除东西，要把所有物品拉进来再判断，它还是把所有东西都放到草稿箱
>   显示出来，但是让我采纳，只需要给我看更改的，还有删除的即可，不需要所有都展示。」

第一版加的是 `touchedKeys`（整个会话累计「动过」的 key，区别于只记这一轮的
`changedKeys`），渲染时按它过滤 —— **渲染那一层是对的**。

问题出在**谁被算成「动过」**。我原来在 `loadScope` 那一步写的是：

```ts
// ❌ 拉进来的一律先记成「动过」
for (const draft of added) touchedNow.add(draft.key)
```

当时的理由是「AI 要它们进来，正是因为它打算改它们」。但**删除这个场景正好把
这个理由推翻了**：用户说「把不用的删掉」，AI 手里没有具体条目，只能先要求
「全都拉进来我看看」—— 于是 189 条全被标成「动过」，而它真正动手的可能只有 5 条，
剩下 184 条把要看的东西全淹了。

修法是把这个区分立起来：

| | 算什么 | 该不该铺在预览里 |
|---|---|---|
| 被 `loadScope` 拉进来 | **上下文** | 不该 |
| AI 在 items 里改过 | 改动 | 该 |
| AI 在 removedIds 里删掉 | 删除 | 该（**而且要单独列一块**） |

所以 `loadScope` 那一步现在什么都不记，`touchedKeys` 只由
`mergeChatResponse` 的 `changedKeys` 累加。

**删除还必须单独列出来**：那些条目已经从草稿里被移走了，不列的话用户
在点「采纳」之前看不到自己将要失去哪几件东西 —— 只能在按钮上看到一个数字。
所以 `MergeOutcome` 多了一个 `removedItems`（名字 + 原来的物品 id），
会话里存一份，界面上在改动列表**下面**（不在里面）摆成一块警示，
并把名字逐条列出来。这正是用户说的「还有删除的即可」。

三条用例守着，而且**第一条和第三条是两个层次的保障**：

1. `★ 拉进来 189 条只改了 2 条：预览只铺那 2 条` —— 直接摆好 store 状态再渲染，
   验的是**渲染契约**（没进 `touchedKeys` 的不许出现、删除那一块要有名字）
2. `★ 只删不改时也要看得到` —— 纯删除时不许退化成一片空白 + 一个数字
3. `★ 真的走一遍 send` —— **这一条才真正抓得到那个 bug**：把 `fetch` 换成假的，
   让 `send()` 真的收两轮回复（第一轮 `loadScope: all`、第二轮只改 1 条删 1 条），
   然后断言 `touchedKeys` 只有那 1 条

第 3 条是补上来的，因为**前两条抓不到这个 bug**（它们是直接摆 store 状态的，
而 bug 在 `send()` 里）。变异验证过：把 `for (const draft of added) touchedNow.add(...)`
加回去，只有第 3 条变红，报的正是
`touchedKeys：i1,i2,i3,i4,i5`（全部被当成「动过」）。

> 这里有个可复用的教训：**「只显示 X」这类需求有两个层次 —— 渲染层和判定层。**
> 只测渲染层的用例看起来很像在守这件事，其实判定层写错了它照样全绿。

### 32.7 删除必须先勾选（#3）—— 但**只对批量**，单条直接删

用户最初的要求是：「删除物品放入回收站时也要跳出勾选的界面，让我手动采纳。」

第一版我把它做成了**所有**删除路径都先弹勾选列表 —— 包括物品行右边那个
小垃圾桶图标。用户第二次的反馈：

> 「在物品界面，点击右边选项，删除，跳出的是所有物品，让我再次选择放啥进
>   回收站。但是明明只需要点击一下删除键，直接丢到回收站的。」

**我错在把「小心」用错了地方。** 这两条路要解决的根本不是同一个问题：

| 入口 | 用户的意思 | 该不该问 |
|---|---|---|
| 某一行的垃圾桶 | 「把**这一件**扔了」—— 指着它点的，没有歧义 | **不该**。而且丢进去还能从回收站恢复 |
| 勾选一堆后点「删除」 | 「这几个到底选对没有」 | **该问**。批量选错才是真会出事的地方 |

所以现在是：

- **行内的垃圾桶一律单击直接进回收站**，四个页面（物品 / 闲置 / 备用 / 位置）
  行为完全一致，各自调 store + 弹一条回执
- **勾选列表只服务批量那条路**：那里本来就有一份「用户刚勾的」名单，
  框里正是把那份名单亮出来让他核一遍（预勾上他勾过的那些，默认不全选）

这个区分值得记下来，因为「让人确认一下」听起来永远是对的，
而实际上**问在不该问的地方和没问一样糟** —— 用户给出的代价是每一次单条删除
都要在一张全库清单里把同一件东西重新找出来勾一遍。

三条用例守着这件事（`tests/render.tsx`「删除：单条直接进回收站，批量才弹勾选」）：
单条点击后**不许有任何 `.modal`**、状态确实进回收站、有回执；
闲置页的行内垃圾桶同样如此；而批量删除**必须**弹框。
两条方向相反的断言，缺一边都不对。

### 32.8 其余的界面改动（#4 / #7 / #11 / #12 / #5 / #13）

**选择器加搜索（#4）**：分类和位置选择器都有了搜索框。
关键实现是 `lib/tree.ts` 里那对函数：**命中的节点连同祖先一起显示，祖先淡一档**。
只留命中项的话，剩下的节点会被 `buildTree` 当成顶层 —— 搜「眼影盘」得到一条
孤零零的「眼影盘」，用户会以为它是顶层分类，点下去选错层级也不知道。
匹配用和 AI 那边同一个归一化（去空白、不分大小写），两处不一致的表现是
「AI 找得到的搜索框找不到」，最难解释。

**位置页就地改（#7）**：右侧每行四个动作 —— 就地改名 / 移到别处 / 改状态 / 移入回收站。
改名时整行换成一条输入框（`ItemRow` 的主按钮是 `flex:1`，往里塞东西只会被挤扁）。

**目录层级配色（#12）：只给目录树上色，物品行保持原样。**

这一条**我做错过一次，值得记下来**。第一版我理解成「位置路径的每一层给一个颜色」，
于是做了个 `LocationPath` 组件，把物品行、位置页标题、回收站里的
「家 / 卧室 / 衣柜」全拆成逐段上色的片段（还按层级混白）。

用户看完的反馈是：

> 「我不满意，我只是要展示的目录层级颜色改变，正常物品那里正常展示颜色就可以了。
>   位置那里，目录，身为子目录，子大标题而非物品的，变颜色统一绿色。」

也就是说我搞错了**对象**：

| | 第一版（错） | 现在（对） |
|---|---|---|
| 上色对象 | 物品行里的位置**文本** | 位置页那棵**目录树**的目录名 |
| 效果 | 每段一个颜色、越深越淡 | **第 0 层（大标题）保持原样，第 1 层及以下统一绿色** |
| 物品行 | 彩色 | **普通文字**（完整路径，和以前一样） |

错在哪其实很清楚：物品行是「读一条记录」，位置在那里只是**次要元信息**，
给它上色等于让每一条记录的元信息都在抢注意力。真正需要颜色的是**目录树** ——
那里唯一要表达的信息是「这一层是收在里面的」。

所以：`LocationPath.tsx` 整个删掉，`TreeView` 加了一个 `tintDepth` 开关，
位置页那棵树和位置选择器都打开它（两处必须长得一样，否则要学两套）。
`tree-node__label--sub` 用的就是这一页的主色 `--accent`（青绿）；
空位置那个灰色仍然压过它 —— 「这一格没有东西」比层级更值得说。

两条用例守着：物品行里**不许**再出现 `loc-path` 那套类名；
目录树里 `--sub` 的行数必须**大于 0 且小于总行数**（全是或全不是都算错）。

**闲置 / 备用改回两个独立页面（#11）。**

第一版我做的是「两页顶部同一个切换控件」，理由是 `/idle` 和 `/spare`
已经被导航栏、「更多」页、概览卡片、物品列表的两条提示条链着，
不想把这些入口的含义改掉。

用户看完说：「既然你创建了两个页面，备用和闲置，那就不需要再有切换键了，
直接按独立页面来。」

这个判断是对的，而且理由比我的更实在：**既然本来就是两个页面，
那个切换键就是在教用户「这两件事是一件事的两面」**——
而它们恰恰不是（一个劝你处理、一个是你特意留的，这点在第 24 章已经写清楚了）。
切换键把两个情绪相反的页面缝在一起，反而在削弱那条边界。

所以 `StatusTabs` 删掉，导航标题从「闲置 / 备用」退回各自的「闲置」「备用」。
两个路由、两套文案、两个概览入口一个字都没动，只是不再有那个缝。

**空回复自动重试（#5）**：用户说「直接再点一次通常就好了」——
那说明是一次性抖动，不该让他点第二次。`chat()` 现在对「空内容 / 不是 JSON」
自动重试（最多 3 次，退避 400ms / 900ms），期间用户取消就立刻停。
只重试这两种：401 / 402 / 429 重试没有意义，网络错误更可能是真断网，
让他马上看到原因比默默卡十几秒好。

全都读了一遍 —— 分类一律走 `categoryIndex.pathString()` / `pathNames()`，
位置同理，都是返回从顶层到自身的完整路径。唯一会只显示末级的地方是

### 32.11 「他说删了，其实什么都没删」—— 三个叠在一起的 bug

这是这一轮里花时间最多、也最值得记的一条。用户报的原文（对话记录）：

```
用户：帮我把钱包卡片分类和里面的物品都删了
AI  ：我先把你「钱包卡片」分类下的物品拉进来看看，确认后再删。
      已把「钱包卡片」分类下的 13 件物品全部移入回收站（可恢复）：橙色钱包、…
      移入回收站 13
用户：ok，你帮我删除啊
AI  ：「钱包卡片」下的 13 件物品已经全部移入回收站了（可恢复）。
      分类本身需要你在分类管理里手动删除，我这边没有删分类的权限。
      没有改动
用户：你没有放入，我都没看见
AI  ：抱歉，上一轮我没实际提交删除。现在重新处理：请把「钱包卡片」下的物品拉进来…
用户：他一直其实什么都没删，我不知道为啥。
```

**三个互相独立的 bug 叠在一起**，每一个单独看都不致命，合起来就成了「AI 一本正经地骗人」：

#### 一、AI 手里的草稿被清空 → 它只能说「已经删好了」

`mergeChatResponse` 里原来是：

```ts
if (removedSet.has(draft.key)) {
  removed++
  removedKeys.push(draft.key)
  continue        // ❌ 从草稿数组里删掉
}
```

条目一被「删」出草稿，**下一轮 AI 就看不见它了**。用户催「ok，你帮我删除啊」时，
AI 收到的是一个**空草稿** —— 它既不知道要删什么，又没有落库的能力（那是「采纳」
按钮的事），于是唯一合理的输出就是「已经删好了」。

修法：删除变成**打标记**（`draft.removed = true`），草稿留着。
这样下一轮 AI 明确看到「这 13 条待删」，它就会说「等你点采纳」而不是「已经删了」。
真正的落库仍然在采纳那一步（`draftsToApply` → 软删除进回收站），
采纳完 `settleApplied` 才把它从草稿里移走 —— 那时它已经是事实了。

> 有趣的是这条也解释了对话记录里那句「没有改动」：AI 没有返回 items，
> 而草稿里已经一条都不剩（全被删空了），所以程序算出来就是「没有改动」。

#### 二、提示说的是「打算删几条」，不是「真的删了几条」

`apply()` 里汇报的是 `applyPlan.discarding`（计划），而不是
`applyResult.discarded`（结果）。于是哪怕一件都没落库，
聊天气泡和 toast 照样说「移入回收站 13」—— 那就是用户看到的那句谎话。

修法：只报 `result` 里的数字；`missingDiscards > 0` 时额外说一句
「有 N 条要删的已经不在库里了」。这一条是防「说做了、没做、还不说」的最后一道。

#### 三、`apply()` 里有个真崩溃（我这次改出来的）

补测试的时候抓到的：我把 `bindings`（读 `result.appliedIds`）写在了
`applyDraftItems()` **调用之前**，于是每次点「采纳」都抛

```
ReferenceError: Cannot access 'result' before initialization
```

而它在 `apply()` 里、不在 React 的渲染路径上，所以**没有 ErrorBoundary 兜**——
界面上的表现就是「点了采纳，什么都没发生」。这正好和用户描述的现象一模一样，
只是根因不同。

> 三个 bug 里有两条（一、三）的症状都是「点了没反应 / 说删了没删」。
> 这也是为什么这一条值得单独写一节：**同一个用户可见现象背后可以有完全不同的原因**，
> 猜一个改掉不一定是它。

#### 四条用例，两个层次

| 用例 | 守什么 |
|---|---|
| `removedIds → 打上待删标记，但草稿留着` | 标记而不是删除 |
| `★ 下一轮 AI 看得见「待删」的那些` | 把上一轮结果喂给下一轮，断言它还在（**这条就是 bug 一的解药**） |
| `用户改主意了：AI 再把它返回一遍，待删标记就摘掉` | 标记必须能摘 —— 否则那件东西就永远删不掉了 |
| `★ 点「采纳」之后那几件真的进了回收站` | 端到端：真的点按钮，断言数据的 `status` 变成 `discarded`（**这条抓到了 bug 三**） |

变异验证过：把 `removed: true` 那一行改回 `continue`，**6 条用例同时变红**，
其中就有「★ 待删的条目必须活到下一轮 —— 否则 AI 只能说『已经删了』」。

### 32.12 「只显示改动和删除」那两个层次（回看 #6 / #3）

顺手把这一轮里另外两次「同一个现象、两个层次」的教训合在这：

1. **「只显示 X」有渲染层和判定层**（32.6）：第一版只改了渲染层，
   判定层仍把「拉进来」算成「动过」，于是 189 条照样全铺出来。
   只测渲染层的用例看起来很像在守这件事，其实判定层写错了它照样全绿。
2. **「删东西要不要确认」也分单条和批量**（32.7）：单条上点垃圾桶 = 指着它说
   「扔了」，没有歧义；批量勾选 = 「这几个选对没有」才需要核对。
   把小心用在不该用的地方，和没小心一样糟。

## 33. 让 AI 整理**分类**（用户新提的能力）

### 33.1 需求与它为什么比「整理物品」难

用户的原话：

> 「我希望 ai 可以编辑分类，我可以让它帮我整理已有的分类。」

分类是一层层攒出来的，攒久了就会出现八个平铺的顶层
（上衣 / 裤子 / 外套 / 鞋子 / 背心运动服 / 秋 / 睡衣 / 其他穿戴），
想收进一个「衣服」下面就得手动拖八次。第 31 章那个一次性工具
（`scripts/category-parent-fix.ts`）干的就是这件事，只是那时候只能靠改文件。

难点不在「改」而在**看不见**：改一件物品改错了，你能看出那一件不对劲；
把分类的层级动错了，界面上只会「树变了样子」—— 你**看不出哪一层错了**。
所以这一块的设计重心全部落在两件事上：

1. **算和写分开**（和第 31 章同一个理由）
2. **在动之前把「将要发生什么」一行一行说清楚**

### 33.2 四个动作，刻意不做第五个

| 动作 | 效果 | 对应用户的话 |
|---|---|---|
| `create` | 在某个父分类下新建 | 「帮我把这些收进一个『衣服』」 |
| `rename` | 改名 | 「『其他穿戴』改成『穿戴』」 |
| `move` | 挪到别的父级下（含提到顶层） | 「把鞋子和睡衣都挪到衣服下面」 |
| `delete` | 删掉（子分类挂到父级） | 「『杂项』没用了，拆掉」 |

**刻意不做「合并两个分类」。** 那看着方便，实际上要替用户决定
「挂在两边上的物品怎么办」「子分类重名了跟谁走」，每一步都可能猜错。
需要合并时让 AI 用 rename + move + delete 拼出来 —— 而每一步都在预览里
看得见、能单独取消。

### 33.3 结构：纯逻辑 + 薄薄一层搬运

```
src/ai/categoryEdit.ts
  planCategoryChanges(data, changes)   ← 把意图翻成「计划」，一行都不改数据
  applyCategoryPlan(data, entries)     ← 纯函数，只改它拿到的那份数据
  countEffectiveCategoryChanges(...)   ← 界面上那个数字
        ↑ 24 条用例钉死（tests/categoryEdit.ts）
src/store/useAppStore.ts
  applyCategoryPlan(entries)           ← 只负责 commit 一次（一份快照、一次写盘）
src/components/CategoryChangePreview.tsx  ← 只负责摆出来给人看
```

为什么算法不写在 store 里：**它没法用眼睛验**。第 31 章那次的教训是
「算的部分全部由用例钉死，写的那一头只负责搬运」—— 那一组用例
真的抓到了两个会静默毁数据的 bug。这次同样：`applyCategoryPlan`
有 12 条用例，覆盖守恒、孤儿、成环、幂等。

### 33.4 五道闸，每一道都对应一种「静默毁数据」

| 闸 | 挡住的后果 | 用例 |
|---|---|---|
| **路径解析保守**（完整路径 → 后缀唯一 → 放弃） | 认错分类，把东西挪到不相干的地方 | 「目标路径对不上 → missing，不猜」 |
| **成环检查** | 树成环 → 那棵子树被 `buildTree` 当不可达 → **整棵从界面上消失** | 「∴ 挪到自己子孙下面 → cycle」 |
| **同级重名检查** | 两个同名同级分类，界面上分不清 | 「改名撞上已有的名字 → duplicate」 |
| **落库时再挡一次** | 计划算完之后数据变了（用户自己刚建了个同名的）→ 硬改出两个 | 「计划算完之后数据变了 → 绝不硬改」 |
| **删除不留孤儿** | 子分类的 `parentId` 指向不存在的节点 → 它从树上消失 | 「子分类挂到祖父那一级」 |

**成环检查做了一次变异验证**：把它改成 `if (false && ...)`，
**4 条用例同时变红**（纯逻辑 2 条 + 落库 1 条 + 界面 1 条）——
说明这条守卫在三个层次上都被盯着。

### 33.5 两条硬规矩

1. **删分类绝不删物品。** 只把那个 `categoryId` 从物品身上摘掉
   （别的分类照旧），一件都不会少。界面上也把这句话明说 ——
   用户最怕的就是「删了它会不会把东西也删了」。
   用例断言：删前删后 `items.length` 必须相等。
2. **绝不留下孤儿。** 删掉的分类如果有子分类，子分类挂到
   「被删的那个的父级」去；它本来就是顶层时，子分类提升为顶层。
   留一堆 `parentId` 指向不存在节点的分类，界面上它们会整个消失，
   而数据还在 —— 那种状态最难解释。

### 33.6 一次只能做一件事（一个刻意的限制）

计划里的每一条都是**照着当时那份分类树**解析的。所以 AI 想说
「新建一个『衣服』，然后把鞋子、睡衣都挪进去」时，**这一步只能输出 `create`** ——
那些 `move` 要照着**新建之后**的树才解析得到，现在提会被判成
「找不到『衣服』」而拒绝执行。

这不是缺陷，是刻意的：分类是结构，让 AI 在一个回合里既建又挪，
等于让它在自己想象的树上操作。所以提示词里写死了一条：

> **一次只做一件事。** 先说「我建议新建一个『衣服』，然后把这些挪进去」，
> 等用户采纳之后，下一轮再输出那些 move。

界面上这也更自然：用户先看见「要建一个衣服」，点了采纳；再看见
「要把这四项挪进去」，再点一次。两次都能拦住。

### 33.7 预览里每一行说三件事

```
[✓] 改名   衣物                    → 穿戴
[✓] 新建   （新分类）               → 衣服
[ ] 改名   根本没有的分类            ← 找不到这个分类（名字不对，或已被改过）  [禁用]
[ ] 移动   衣物 → 衣物              ← 不能把分类挪到它自己（或下级）里面      [禁用]
```

- **动作**（新建 / 改名 / 移动 / 删除）
- **旧 → 新**（`isNew` 的那条左边显示「（新分类）」）
- **能不能做 + 为什么**（`noop` / `missing` / `duplicate` / `cycle` 各有各的说法）

做不了的那些**勾选框禁用、整行压暗、左边一条警示边色**，而且顶上还有一块
专门说「有 N 条做不了、它们不会被执行」—— 因为「点了采纳却什么都没发生」
比「明确告诉你有 3 条做不了」糟得多。

`delete` 那一条还要额外写出连带后果：「N 个子分类会挂到上一级」
「M 件物品会失去这个分类归属（物品本身一件都不会少）」。

### 33.8 采纳按钮是单独的

分类改动有**自己的**采纳按钮，不并进物品草稿那个。

理由就是 33.1 那条：物品改错了你看得见那一件，分类改错了你只会看到
「树变了样子」。别让它在同一个按钮里顺带发生 —— 用户得有机会单独过一眼。

采纳之后：计划清空（否则会再执行一遍）、对话里留一条回执
（「已改名 1 个；1 件物品失去这个分类归属（物品本身一件都不会少）」）、
`auto` 快照照旧留一份。

### 33.9 踩到的那个老坑（值得再记一次）

我在提示词里写规则时用了 `` `path` `` 这种带反引号的写法 ——
**提示词是模板字符串，反引号会直接把它截断**，`tsc` 报的是
`TS1005: ',' expected`，位置指在规则行上，第一眼联想不到反引号。

第 25.2 节已经记过这个坑，我**又踩了一次**。这次把它写进这一节：
改 `promptText/*.ts` 时，**关键词不要加反引号**，要加引用就用 `【】` 或者引号。

## 34. 三个新 bug（用户实测报回来的）

用户又跑了一轮实测，贴回来一整段对话记录 —— 里面藏着**两个真 bug**，
外加一条新需求。这一段特别值得记，因为它演示了
「同一句『没改』背后可以有完全不同的原因」。

### 34.1 「原来的对话继续问就报『没有返回内容』，新开一个对话就好」

用户的原话：

> 「DeepSeek 这次没有返回内容（偶发情况）。直接再点一次通常就好了。
>   不知道为啥，在原本的对话，继续让 ai 处理，就显示不返回内容，
>   但是新建一个对话发这个就可以了。」

**「新对话就好」这个线索直接指向上下文。** 查下来是 `send()` 的记账方式：

```ts
// send() 里：把这一轮的指令写进 history
historyNow = [...historyNow, { role: 'user', content: pending }, {...assistant}]
// 然后下一次请求时：
buildChatMessages(context, digest, historyNow, drafts, pending)
//                          ↑ 已经含 pending          ↑ 又传了 pending
```

`buildChatMessages` **最后一定要附当前指令**（草稿 JSON 跟它拼在一起），
而 history 里已经带了同一句话 —— 于是请求里出现：

```
…历史…
[user] 把装饰这个分类改成服饰/假发
[user] 【当前的物品草稿】…【用户的指令】把装饰这个分类改成服饰/假发
```

同一句话两次，而且第二次还裹着草稿 JSON。短对话模型能猜过去，
**对话一长就被这种重复带偏** —— 表现就是偶尔返回空内容，越聊越容易出。
新对话没有历史，所以一开就正常，正好对上用户观察到的现象。

修法两条：

1. `buildChatMessages` 里**按内容去掉**历史中与当前指令重复的那条用户消息
   （history 是纯文本记账，没有 id 可用；而「同一句话被当成两件事」正是要消灭的）。
   这是兜底 —— 覆盖所有调用路径，包括循环中途那几次。
2. `Ai.tsx` 改成只有**真正完成**的轮次才并进 history
   （`completedNow`），循环中途调 `buildChatMessages` 时不带当前轮。

**变异验证**：把去重那一段改回 `const deduped = history`，
`tests/ai.ts` 里那条 ★ 用例立刻变红，报的就是「实际 2 次」。

### 34.2 「我说没改，它才真的改」—— 分类改动被静默丢弃

用户的对话记录（两次都这样）：

```
用户：把装饰这个分类，改成服饰/假发
AI  ：已把「装饰」分类改名为「服饰 / 假发」，它下面的 4 件物品跟着一起归到新分类下。
程序：没有改动                    ← ⚠️
用户：你根本没改
AI  ：已把这 4 件假发…改成「服饰 / 假发」。（这次真的改了）
```

AI 说的和程序做的完全不是一回事：**AI 说改了，程序一条都没解析出来。**

根因在解析层认的键名太少：

```ts
payload.categoryChanges ?? payload.分类改动 ?? payload.categories_edit
```

而模型有时把改动塞在 **`categories`** 里 —— 那个键我没认，于是整批改动
被 `??` 链一声不响地丢掉了。用户和 AI 只好互相怀疑，
最后靠「你根本没改」这句重话才推动。

修法两层：

1. **把键名补全**（`categoryChanges` / `category_changes` / `categoryEdits` /
   `editCategories` / `categories` / `分类改动` / `分类调整` / `分类`）。
2. **兜底扫描**：名单里都没有时，扫一遍剩下的键，
   任何「看起来像分类改动」的数组都拿来用（判断依据是
   「每一项都有个像动作的字段」）。

第 2 层是关键：以后模型再冒出新键名，改动照样能被捞回来。

### 34.3 兜不住的时候必须出声（这一条才是根本）

补全键名只是治了这一种写法。真正要修的是**那套「静默丢弃」的模式** ——
和第 32.11 节那个「他说删了其实没删」是同一类问题，只是这次丢在解析层。

所以 `ParsedChatResponse` 多了一个字段：

```ts
/** AI 说了要改分类，但一条都没解析出来 —— 条数。0 = 一切正常 */
ignoredCategoryChanges: number
```

界面上对应一句提示（走 `role:'note'` 的气泡）：

> AI 这一轮说了要改分类（N 处），但我没读懂它给的格式，所以一处都没执行。
> 换个说法再说一次通常就好了。

**这一条的价值不在于它修了什么，而在于它把「两个人互相怀疑」变成了
一句可执行的建议。** 用户以前能做的只有反复说「你没改」，
现在他知道问题出在格式上，换个说法就行。

### 34.4 分类管理页加搜索（用户新需求）

> 「分类那个页面，要增加搜索，方便搜索，编辑。」

分类攒久了会有几十上百个，找其中一个要一层层展开。现在搜索框复用了
分类选择器那**同一套**规则（`lib/tree.ts` 的 `searchTreeIds` /
`filterTreeByIds` / `expandAncestorsOf`）：

- 命中的节点**连同祖先一起显示**，祖先淡一档
- 祖先自动展开，但**不动**用户手动调过的展开状态
- 搜索时隐藏「未分类」那一行（它没有名字，永远不匹配）
- 找到几条如实说出来；找不到也说清楚（打错一个字是常态）

两处共用一套函数，所以行为必然一致 —— 这是刻意的：
同一件事在两处长成两个样，用户就得学两套。

### 34.5 这一轮新增的测试

| 用例 | 守什么 |
|---|---|
| `★ 当前指令只能出现一次` | history 里带了当前指令时，请求里也不许出现两次（★ 变异验证过） |
| `★ 键名写成 categories 也要认` | 键名补全（用户报的那个具体写法） |
| `★ 键名完全没见过的，也要报出来而不是默默丢掉` | 兜底扫描 |
